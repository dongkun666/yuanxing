## 2. 性能瓶颈分析

### 2.1 前端性能瓶颈

#### 2.1.1 首屏加载
- **问题**: 页面首次加载需要加载多个 JS 文件，串行加载导致首屏时间长
- **影响**: 新用户首次访问体验差，跳出率高
- **严重程度**: 高
- **当前状态**: 多个脚本通过 `loadScript` 动态加载，无预加载机制

#### 2.1.2 视图切换
- **问题**: 视图切换时每次都需要 fetch HTML，无缓存或预加载
- **影响**: 页面切换有明显延迟，用户体验不流畅
- **严重程度**: 中高
- **当前状态**: 有 viewCache 但仅缓存 HTML，无预加载策略

#### 2.1.3 数据重复请求
- **问题**: 相同数据在不同视图中重复请求，无前端缓存
- **影响**: 网络请求冗余，页面加载慢
- **严重程度**: 中
- **当前状态**: 无统一的数据缓存层

#### 2.1.4 图片资源
- **问题**: 图片未做懒加载和优化
- **影响**: 列表页滚动时图片加载慢
- **严重程度**: 低
- **当前状态**: 无懒加载实现

### 2.2 后端性能瓶颈

#### 2.2.1 数据库查询
- **问题**: 部分复杂查询缺少索引，N+1 查询问题
- **影响**: 列表页和详情页响应慢
- **严重程度**: 高
- **当前状态**: 主要表已有基础索引

#### 2.2.2 搜索性能
- **问题**: ES 查询在数据量大时可能较慢
- **影响**: 搜索响应时间长
- **严重程度**: 中高
- **当前状态**: 使用 ES 全文检索

#### 2.2.3 合同审查
- **问题**: AI 审查计算量大，同步请求可能超时
- **影响**: 用户等待时间长
- **严重程度**: 中
- **当前状态**: 同步处理

## 3. 优化建议

### 3.1 前端优化

#### 3.1.1 资源预加载 (优先级: 高)
**实施方案**:
- 在 index.html 中添加关键资源的 `<link rel="preload">`
- 对 router.js 中的常用视图添加预加载逻辑
- 使用 Intersection Observer 实现图片懒加载

**预期收益**:
- 首屏加载时间减少 20-30%
- 视图切换更流畅

#### 3.1.2 数据缓存优化 (优先级: 高)
**实施方案**:
- 在 utils.js 中添加统一的缓存工具函数
- 实现内存缓存 + localStorage 二级缓存
- 添加缓存过期和失效机制
- 对 API 请求结果进行缓存

**预期收益**:
- 重复请求减少 50% 以上
- 页面二次访问速度显著提升

#### 3.1.3 路由预加载 (优先级: 中)
**实施方案**:
- 根据用户行为预测下一个可能访问的视图
- 在空闲时间预加载视图 HTML 和 JS
- 实现智能预加载策略

**预期收益**:
- 视图切换几乎无延迟
- 用户体验更接近原生应用

#### 3.1.4 代码分割和按需加载 (优先级: 中)
**实施方案**:
- 将大的 JS 模块拆分为更小的 chunk
- 按功能模块按需加载
- 优化首屏必须的代码量

**预期收益**:
- 首屏 JS 体积减少 30-40%
- 首屏可交互时间提前

### 3.2 后端优化

#### 3.2.1 数据库优化 (优先级: 高)
**实施方案**:
- 分析慢查询，添加缺失的索引
- 优化 N+1 查询，使用 JOIN 或预加载
- 添加查询缓存层（Redis）
- 对常用统计数据做预计算

**预期收益**:
- API 响应时间减少 40-60%
- 数据库负载降低

#### 3.2.2 搜索优化 (优先级: 中)
**实施方案**:
- 优化 ES 索引配置
- 添加搜索结果缓存
- 实现搜索建议的前缀缓存
- 分页查询优化

**预期收益**:
- 搜索响应时间减少 30-50%
- 搜索并发能力提升

#### 3.2.3 异步处理 (优先级: 中)
**实施方案**:
- 合同审查改为异步任务队列
- 使用 WebSocket 或轮询推送结果
- 大文件上传使用分片上传

**预期收益**:
- 用户无需等待即可继续操作
- 系统并发能力提升

## 4. 优化效果验证

### 4.1 性能指标定义

| 指标 | 定义 | 目标值 | 测量方式 |
|------|------|--------|----------|
| FCP | First Contentful Paint | < 1.5s | Lighthouse |
| LCP | Largest Contentful Paint | < 2.5s | Lighthouse |
| FID | First Input Delay | < 100ms | Lighthouse |
| CLS | Cumulative Layout Shift | < 0.1 | Lighthouse |
| TTI | Time to Interactive | < 3.5s | Lighthouse |
| API 响应时间 | P95 响应时间 | < 500ms | 后端监控 |
| 页面切换时间 | 视图切换耗时 | < 300ms | 前端埋点 |

### 4.2 验证方法

#### 4.2.1 前端性能测试
使用 Lighthouse / WebPageTest 进行测试：
```bash
# 使用 Lighthouse CLI
npx lighthouse http://localhost:8080 --view --preset=desktop

# 对比优化前后
# 优化前: 保存 baseline 报告
# 优化后: 重新测试，对比指标
```

#### 4.2.2 后端性能测试
使用压力测试工具：
```bash
# 使用 wrk 进行 API 压力测试
wrk -t4 -c100 -d30s http://localhost:3847/api/cases

# 测试搜索接口
wrk -t4 -c50 -d30s -s search.lua http://localhost:3847/api/search
```

#### 4.2.3 用户体验测试
- A/B 测试对比优化前后的用户行为数据
- 收集用户反馈
- 监控关键业务指标（转化率、留存率等）

### 4.3 优化验收标准

1. **首屏加载**:
   - FCP < 1.5s
   - LCP < 2.5s
   - TTI < 3.5s

2. **API 性能**:
   - P95 响应时间 < 500ms
   - 错误率 < 0.1%

3. **用户体验**:
   - 页面切换时间 < 300ms
   - 搜索响应时间 < 1s
   - 无明显布局偏移 (CLS < 0.1)

4. **业务指标**:
   - 跳出率降低 10% 以上
   - 用户停留时间增加 15% 以上
   - 核心功能转化率提升 5% 以上

### 4.4 监控和持续优化

#### 4.4.1 性能监控
- 前端性能数据上报（Navigation Timing, Resource Timing）
- 后端 API 响应时间监控
- 错误率和异常监控
- 用户体验指标（RUM）

#### 4.4.2 性能预算
制定性能预算，防止性能回退：
- JS 总大小 < 200KB (gzip)
- CSS 总大小 < 50KB (gzip)
- 首页请求数 < 30
- API P95 < 500ms

#### 4.4.3 定期审计
- 每周自动运行性能测试
- 每月进行全面性能审计
- 每季度更新性能优化计划
