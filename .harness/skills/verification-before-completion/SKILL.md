# Verification Before Completion — 完成前验证

**核心理念（Superpowers）：用证据而非声明，确保真正修复了问题。** 验证不是"走个过场"，而是系统化地证明代码确实做了它该做的事，并且没有破坏任何它不该破坏的事。完成的标准不是"我觉得可以了"，而是"我有证据证明它可以了"。

> "验证是工程师的诚信。说它能用不算数，证明它能用才算数。" —— Superpowers 工程实践

---

## 何时激活

### 必须激活（强场景）

- 任何功能开发完成，准备宣布"做完了"之前
- 任何 bug 修复完成，准备结束调试之前
- 重构完成，准备提交/合并之前
- 一个 Plan track 完成，准备进入下一个 track 之前
- 请求代码审查之前的最后一道自检
- 用户明确说"验证一下"、"确认没问题"、"确保能跑"
- 任何你准备说"完成了"的时刻

### 建议激活（中场景）

- 阶段性开发告一段落，准备暂停切换任务
- 修复了一个复杂 bug，心里不太确定是否彻底
- 改动涉及多个模块，担心有副作用
- 改动了核心/基础组件，影响范围广
- 上线前的最终检查

### 跳过（弱场景）

- 还在开发过程中，远未完成
- 纯文档修改，不涉及代码逻辑
- 单文件 typo 修复，一眼就能确认没问题
- 纯探索性代码，本来就是 throwaway 的

## 验证层次模型

验证不是单点检查，而是一个**从内到外、从低到高**的多层次体系。每一层都有它的价值，也都有它的局限。**只做某一层验证是不够的。**

```
┌─────────────────────────────────────────────────┐
│           第 4 层：手动验证（Manual）            │  ← 用户视角、真实场景
│  手动操作、探索性测试、UX 检查、边界场景尝试      │
├─────────────────────────────────────────────────┤
│         第 3 层：端到端测试（E2E）              │  ← 完整用户流程
│  完整业务流程、跨系统交互、真实环境模拟          │
├─────────────────────────────────────────────────┤
│        第 2 层：集成测试（Integration）         │  ← 模块间协作
│  模块集成、数据库交互、API 调用、外部依赖        │
├─────────────────────────────────────────────────┤
│        第 1 层：单元测试（Unit）                │  ← 最小功能单元
│  单个函数/类、快速反馈、高覆盖率、边界条件        │
└─────────────────────────────────────────────────┘
```

**原则：从低层到高层，层层递进。低层不通过，高层不用测。**

---

### 第 1 层：单元测试（Unit Testing）

**目标：验证最小功能单元的正确性。** 一个函数、一个类、一个组件，隔离所有外部依赖，确保它在各种输入下的行为都符合预期。

#### 单元测试的价值

- **快速反馈** — 几秒到几十秒就能跑完，改完立刻验证
- **精准定位** — 失败了就知道具体是哪个函数出问题
- **边界覆盖** — 容易覆盖各种边界条件和异常场景
- **设计驱动** — 好的单元测试倒逼写出好的、可测试的代码

#### 单元测试的检查清单

- [ ] 所有单元测试全部通过
- [ ] 新增的代码有对应的单元测试覆盖
- [ ] 修复的 bug 有对应的回归测试
- [ ] 覆盖了正常路径、边界情况、异常输入
- [ ] 测试的是行为，不是实现细节
- [ ] 每个测试独立、可重复、不依赖顺序

#### 常见的单元测试不足

- ❌ 只测"开心路径"，不测异常和边界
- ❌ 测试和实现耦合太紧，一改代码测试全挂
- ❌ 一个测试测太多东西，失败了不知道哪错了
- ❌ 断言太宽松，只判断"不报错"，不判断具体结果

---

### 第 2 层：集成测试（Integration Testing）

**目标：验证模块之间的协作是否正常。** 单元测试保证每个零件都没问题，集成测试保证零件组装起来也没问题。

#### 集成测试验证什么

- 模块间的接口调用是否正确
- 数据库查询/写入是否符合预期
- API 请求/响应格式是否正确
- 第三方服务集成是否正常
- 消息队列、缓存等中间件交互

#### 集成测试的检查清单

- [ ] 关键集成路径有测试覆盖
- [ ] 数据库 CRUD 操作验证通过
- [ ] API 接口输入输出格式正确
- [ ] 错误处理和降级逻辑正常
- [ ] 事务、并发等场景正确处理

#### 集成测试 vs 单元测试

| 维度 | 单元测试 | 集成测试 |
|---|---|---|
| **测试对象** | 单个函数/类 | 多个模块协作 |
| **外部依赖** | mock 掉 | 用真实的（或测试用的） |
| **运行速度** | 快（秒级） | 慢（分钟级） |
| **失败定位** | 精准 | 需要排查 |
| **覆盖难度** | 容易覆盖边界 | 难覆盖所有组合 |
| **核心价值** | 逻辑正确性 | 协作正确性 |

---

### 第 3 层：端到端测试（E2E Testing）

**目标：从用户视角验证完整业务流程。** 模拟真实用户的操作路径，验证整个系统（前端+后端+数据库+外部服务）作为一个整体是否正常工作。

#### E2E 测试验证什么

- 完整的用户旅程（signup → login → 使用功能 → logout）
- 跨页面/跨服务的业务流程
- 数据在系统各层之间的流转
- 生产环境下的真实行为

#### E2E 测试的检查清单

- [ ] 核心业务流程有 E2E 测试覆盖
- [ ] 关键用户路径走通
- [ ] 前端到后端到数据库的数据一致性
- [ ] 错误场景的用户体验（错误提示、回退路径）
- [ ] 测试在类生产环境中运行

#### E2E 测试的局限

- 运行慢，不能频繁跑
- 失败了难定位问题
- 维护成本高
- 难以覆盖所有边界情况

**所以：E2E 测试是补充，不是替代。核心还是单元测试和集成测试。**

---

### 第 4 层：手动验证（Manual Testing）

**目标：发现自动化测试想不到的问题。** 自动化测试只能覆盖你想到的场景，手动测试能发现"用户一用就出问题但你根本没想到要测"的情况。

#### 手动验证做什么

- 按照真实用户的操作习惯走一遍流程
- 尝试"奇怪"的操作顺序和输入
- 检查 UI/UX 是否符合预期
- 验证加载状态、空状态、错误状态
- 感受性能（速度、流畅度）
- 尝试不同的设备/浏览器/屏幕尺寸

#### 手动验证的检查清单

- [ ] 核心功能路径手动走通
- [ ] 空状态、加载状态、错误状态都正常
- [ ] 边界输入和异常输入处理正确
- [ ] UI 视觉效果符合预期（布局、样式、动画）
- [ ] 响应式布局在不同屏幕尺寸下正常
- [ ] 性能感受在可接受范围内
- [ ] 没有控制台错误/警告

#### 探索性测试

手动验证不只是"按步骤点"，更重要的是**带着怀疑的态度去探索**：

- "如果我点快点会怎样？"
- "如果网络断了会怎样？"
- "如果我在这一步刷新页面会怎样？"
- "如果我输入一个超长的字符串会怎样？"
- "如果我连续点十次提交会怎样？"

> 💡 **理念：** 手动验证的目标不是"证明它能用"，而是"努力证明它不能用"。如果你努力尝试都找不到问题，那它可能真的没问题。

## 验证清单模板

每次完成任务时，使用以下清单进行系统性验证。**一项一项打勾，不要跳步，不要靠记忆。**

### 📋 完整验证清单

#### 第一部分：测试验证

- [ ] **单元测试全部通过**
  - [ ] 运行了完整的单元测试套件
  - [ ] 没有失败的测试
  - [ ] 没有跳过的测试（或者跳过的有充分理由）

- [ ] **新功能有测试覆盖**
  - [ ] 新增的代码有对应的单元测试
  - [ ] 覆盖了正常路径
  - [ ] 覆盖了边界情况（空值、极值、异常输入）
  - [ ] 覆盖了错误处理路径

- [ ] **回归测试通过**
  - [ ] 现有测试全部通过，没有因为改动而挂掉
  - [ ] 修复的 bug 有专门的回归测试
  - [ ] 相关模块的测试也跑了，不只是直接改的那个

- [ ] **集成测试通过（如果有）**
  - [ ] 数据库交互正常
  - [ ] API 接口调用正常
  - [ ] 外部服务集成正常

- [ ] **E2E 测试通过（如果有）**
  - [ ] 核心用户流程通过
  - [ ] 关键场景验证通过

---

#### 第二部分：功能验证

- [ ] **核心功能手动验证**
  - [ ] 主要功能路径走通
  - [ ] 功能行为符合预期
  - [ ] 和需求/设计文档一致

- [ ] **边界情况验证**
  - [ ] 空输入 / 空数据
  - [ ] 最小/最大值
  - [ ] 超长输入 / 大量数据
  - [ ] 特殊字符 / 非法输入

- [ ] **错误处理验证**
  - [ ] 输入错误时有清晰的提示
  - [ ] 网络错误时有合理的降级
  - [ ] 服务器错误时不会崩溃
  - [ ] 错误信息对用户友好（不暴露技术细节）

- [ ] **状态验证**
  - [ ] 加载状态正常（loading 提示、骨架屏）
  - [ ] 空状态正常（空列表、无数据提示）
  - [ ] 错误状态正常（错误提示、重试按钮）
  - [ ] 成功状态正常（成功提示、跳转逻辑）

---

#### 第三部分：质量验证

- [ ] **代码质量检查**
  - [ ] Linter 检查通过，没有 error
  - [ ] 代码格式化符合项目规范
  - [ ] 没有遗留的调试代码（console.log、print、debugger）
  - [ ] 没有注释掉的大段代码
  - [ ] 命名清晰，可读性良好

- [ ] **性能初步检查**
  - [ ] 页面加载速度在可接受范围内
  - [ ] 关键操作响应及时，没有明显卡顿
  - [ ] 没有明显的内存泄漏
  - [ ] 大数据量下性能不崩

- [ ] **安全初步检查**
  - [ ] 用户输入有校验/转义（XSS 防护）
  - [ ] 敏感信息没有暴露在前端/日志
  - [ ] 接口有权限校验
  - [ ] 没有硬编码的密钥/密码

#### 第四部分：兼容性验证（如适用）

- [ ] **浏览器兼容性**
  - [ ] Chrome 正常

- [ ] **响应式验证**
  - [ ] 桌面端正常（1920px+）
  - [ ] 平板正常（768px - 1024px）

- [ ] **设备兼容性（如需要）**
  - [ ] 触屏设备操作正常

### ✅ 验证完成标准

**所有"必须"项全部通过，才能宣布完成。**

如果有"建议"项没通过，需要：
1. 记录下来哪些没通过、为什么没通过
2. 评估风险
3. 明确后续计划（什么时候补）
4. 告知相关人员

> ⚠️ **红线：** 带着已知的问题宣布完成，等于把问题推给下游。下游的人发现问题再回来找你，成本是你现在就修好的 10 倍。

## 回归测试检查

### 什么是回归测试

**回归测试 = 确保你的改动没有破坏现有功能。**

你改了 A 功能，结果 B 功能坏了 —— 这就是"回归"。回归测试就是防止这种情况发生。

### 回归测试的层次

#### L1：相关测试全部跑一遍（最低要求）
- 改了哪个模块，就把哪个模块的测试全跑一遍
- 改了公共组件，所有用了这个组件的地方都要测
- 改了 API，所有调用这个 API 的前端都要测

#### L2：完整测试套件跑一遍（标准要求）
- 所有单元测试全部通过
- 所有集成测试全部通过
- 所有 E2E 测试全部通过

#### L3：影响面分析 + 针对性验证（高级要求）
- 分析改动可能影响哪些地方
- 对高风险区域做额外的手动验证
- 检查相关的边缘场景

### 回归测试检查清单

- [ ] 所有现有测试仍然通过（不是只看你加的测试）
- [ ] 你分析过改动的影响范围
- [ ] 高风险区域做了额外验证
- [ ] 公共接口/组件的调用方都检查过
- [ ] 数据库 schema 变更后，历史数据兼容性验证过
- [ ] 配置变更后，默认值和向后兼容验证过

### 常见的回归盲点

- ❌ "我只改了一行代码，不会有影响" — 往往就是这一行出问题
- ❌ "这个功能没人用" — 你确定吗？
- ❌ "测试没覆盖到的地方应该没事" — 没覆盖不代表没问题
- ❌ "这是纯重构，行为没变" — 你确定行为真的没变吗？

> 💡 **经验法则：** 你觉得"肯定没问题"的地方，往往就是出问题的地方。多花 5 分钟验证一下，省得后面花 5 小时救火。

## 性能验证

### 为什么要做性能验证

功能对了但太慢 = 功能不可用。用户不会等你 10 秒加载页面，也不会忍受点一下按钮卡 3 秒。

### 性能验证的维度

| 维度 | 说明 | 可接受标准（参考） |
|---|---|---|
| **页面加载** | 首屏加载时间 | < 2 秒（3G 网络下） |
| **交互响应** | 用户操作后的反馈时间 | < 100ms（感知不到延迟） |
| **数据处理** | 大数据量下的处理速度 | 取决于业务场景 |
| **资源占用** | 内存、CPU、网络带宽 | 不导致浏览器/设备卡顿 |
| **并发能力** | 多用户同时使用时的表现 | 取决于业务规模 |

### 性能验证怎么做

#### 1. 感知性能（用户视角）

手动操作，感受一下：
- 页面打开快不快？
- 点按钮有没有明显卡顿？
- 列表滚动流不流畅？
- 切换页面有没有延迟？

**判断标准：** 你自己用着觉得舒服吗？如果连你都觉得"有点慢"，用户肯定觉得慢。

#### 2. 工具测量（客观数据）

- **浏览器 DevTools Performance 面板** — 分析页面加载和运行时性能
- **Lighthouse** — 综合性能评分
- **Network 面板** — 看资源加载时间、请求数量
- **Memory 面板** — 检查内存泄漏
- **后端 profiling** — 分析接口响应时间、数据库查询耗时

#### 3. 常见性能问题检查清单

- [ ] 首屏加载时间在可接受范围内
- [ ] 没有不必要的网络请求
- [ ] 图片/资源有压缩和懒加载
- [ ] 列表/表格大数据量下不卡顿
- [ ] 没有频繁的重排重绘
- [ ] 接口响应时间在可接受范围内
- [ ] 数据库查询走了索引
- [ ] 没有 N+1 查询问题

### 性能验证的常见误区

- ❌ "以后再优化" — 以后 = 永远不。先保证基线性能不退化
- ❌ "功能对了就行" — 慢到没法用的功能等于没有功能
- ❌ "我电脑上挺快的" — 用户的电脑/网络可能比你差
- ❌ "性能优化是后面的事" — 架构层面的性能问题，后面改成本极高

## 安全验证

### 为什么要做安全验证

安全问题不是"会不会遇到"，而是"什么时候遇到"。一个简单的 XSS 漏洞、一个没做权限校验的接口，都可能导致严重后果。

### 常见安全检查项

#### 前端安全

- [ ] **XSS 防护** — 用户输入的内容有转义，不会直接插入 DOM
- [ ] **敏感信息保护** — 密码、token 等不会出现在 URL、日志、localStorage（视情况）
- [ ] **客户端校验不等于安全** — 前端校验是为了体验，后端校验才是真的安全
- [ ] **CSRF 防护** — 关键操作有 CSRF token

#### 后端安全

- [ ] **输入校验** — 所有外部输入都有严格的格式/范围校验
- [ ] **SQL 注入防护** — 使用参数化查询/ORM，不拼接 SQL
- [ ] **权限校验** — 每个接口都验证用户是否有权限操作
- [ ] **认证安全** — 密码哈希存储、token 过期机制、登录失败限流
- [ ] **敏感数据保护** — 密码、密钥等不明文存储、不打日志
- [ ] **速率限制** — 防止暴力破解、爬虫、DDoS

#### 通用安全

- [ ] **没有硬编码的密钥/密码** — 配置在环境变量或密钥管理服务
- [ ] **错误信息不泄露细节** — 给用户看的错误信息不暴露堆栈、内部路径等
- [ ] **依赖包安全** — 没有已知有漏洞的依赖版本
- [ ] **HTTPS** — 生产环境使用 HTTPS

### OWASP Top 10 参考

至少要了解并检查这些最常见的安全风险：

1. 注入攻击（SQL 注入、命令注入等）
2. 认证和会话管理失效
3. 跨站脚本（XSS）
4. 不安全的直接对象引用
5. 安全配置错误
6. 敏感数据泄露
7. 功能级访问控制缺失
8. 跨站请求伪造（CSRF）
9. 使用含有已知漏洞的组件
10. 未验证的重定向和转发

> ⚠️ **重要：** 安全验证不是"做一次就完了"，而是一种思维习惯。写代码的时候就要想着"这样写会不会有安全问题"。

---

## 常见验证陷阱

### ❌ 陷阱 1：验证表面，不验证实质

**表现：** 只看"有没有返回成功"，不看"返回的数据对不对"；只看"页面显示了"，不看"显示的内容对不对"。

**例子：**
- 接口返回 200 就觉得没问题，但其实返回的数据格式错了
- 页面渲染出来就觉得没问题，但其实数据是错的
- 测试通过了就觉得没问题，但测试断言写得太松

**纠正：** 验证要深入。不仅要看"有没有"，还要看"对不对"、"全不全"、"准不准"。

---

### ❌ 陷阱 2：只验证开心路径

**表现：** 只测试"一切正常"的场景，不测试出错、边界、异常的情况。

**例子：**
- 只测输入正确的情况，不测输入错误会怎样
- 只测有数据的情况，不测空数据会怎样
- 只测网络好的情况，不测网络差/断网会怎样

**纠正：** 刻意去想"什么情况下会出问题"，然后去验证那些情况。

---

### ❌ 陷阱 3：我觉得没问题 = 真的没问题

**表现：** "应该没问题吧"、"我觉得可以了"、"逻辑上是对的" — 用感觉代替验证。

**问题：**
- 人是会犯错的，你觉得对的不一定真的对
- 很多问题是"没想到"的问题，靠想是想不出来的
- 没验证过的东西，就是有风险的

**纠正：** 用证据说话。跑测试、手动操作、看数据、看日志。能证明它对，才是真的对。

---

### ❌ 陷阱 4：验证了改的地方，没验证没改的地方

**表现：** 我只改了 A 功能，所以只测 A 功能就行。结果 B 功能坏了。

**问题：**
- 代码之间有依赖关系，改了 A 可能影响 B
- 公共组件、工具函数、基础模块的改动影响范围很广
- 有时候你以为只改了 A，其实不小心动了 B

**纠正：** 做影响面分析。想一想"我改的这个东西，哪些地方会用到？"，然后把相关的地方也验证一下。

---

### ❌ 陷阱 5：测试通过了 = 没问题了

**表现：** 所有测试都绿了，就觉得万事大吉了。

**问题：**
- 测试只能覆盖你想到的场景
- 测试可能写得不好，覆盖率高但质量低
- 很多问题（性能、UX、兼容性）测试测不出来
- 测试本身可能有 bug

**纠正：** 测试是必要条件，不是充分条件。测试通过了还要做手动验证、探索性测试。

---

### ❌ 陷阱 6：验证一次就够了

**表现：** 昨天验证过了，今天改了点小东西就不验证了。

**问题：**
- 哪怕只改一行代码，都可能引入新问题
- "小东西"可能不小
- 上次验证的是旧版本，不是现在这个版本

**纠正：** 每次改动后都要重新验证。改动小就少验证一点，但不能不验证。

---

### ❌ 陷阱 7：用户没说 = 不用验证

**表现：** 需求里没说要考虑性能/安全/兼容性，所以我就不管了。

**问题：**
- 用户没说不代表不需要
- 很多东西是"默认就该有的"，不需要特意说
- 出了问题，用户只会怪你没做好，不会怪自己没说

**纠正：** 专业的工程师会主动考虑那些"用户没说但应该有的"东西。这就是专业和业余的区别。

## LexPrime 项目适配

LexPrime 是前后端分离项目（Python 后端 + JavaScript 前端 + 多个 AI 服务），验证需要分层、跨服务进行。

### 前端验证方法

#### 测试工具栈

- **单元测试：** Vitest / Jest
- **组件测试：** React Testing Library / Vue Test Utils
- **E2E 测试：** Cypress / Playwright
- **性能分析：** Lighthouse、Chrome DevTools

#### 前端验证清单

- [ ] 组件单元测试通过
- [ ] 页面渲染正常，没有 console error
- [ ] 状态管理（Redux/Zustand/Pinia）逻辑正确
- [ ] API 调用和数据处理正确
- [ ] 表单验证和错误提示正常
- [ ] 路由跳转和权限控制正常
- [ ] 响应式布局在不同屏幕尺寸下正常
- [ ] 加载状态、空状态、错误状态都处理了
- [ ] 没有内存泄漏（组件卸载后清理定时器/事件监听）

#### 前端手动验证步骤

1. **启动开发服务器**
   ```bash
   cd frontend
   npm run dev
   ```

2. **走一遍核心用户流程**
   - 登录/注册
   - 主要功能页面
   - 数据增删改查
   - 退出登录

3. **检查各种状态**
   - 断网试试（Network → Offline）
   - 慢网速试试（Network → Slow 3G）
   - 输入非法数据试试
   - 快速操作、连续点击试试

4. **性能检查**
   - 打开 DevTools Performance 面板
   - 录制页面加载和关键操作
   - 看有没有长任务、掉帧

---

### 后端验证方法

#### 测试工具栈

- **单元测试：** pytest
- **集成测试：** pytest + test database
- **API 测试：** pytest + httpx/requests
- **性能分析：** cProfile、py-spy

#### 后端验证清单

- [ ] 单元测试全部通过
- [ ] 集成测试（数据库、缓存、队列）通过
- [ ] API 接口返回格式正确
- [ ] 输入校验和错误处理正确
- [ ] 权限控制和认证正常
- [ ] 数据库查询性能达标（有没有 N+1、有没有走索引）
- [ ] 日志记录完整且不泄露敏感信息
- [ ] 异步任务/定时任务正常运行

#### 后端验证步骤

1. **运行测试套件**
   ```bash
   cd backend
   pytest tests/ -v
   ```

2. **手动测试 API**
   - 用 curl / Postman / httpie 调接口
   - 测正常情况
   - 测异常情况（参数错误、权限不够、数据不存在）

3. **检查数据库**
   - 数据写入正确吗？
   - 数据格式对吗？
   - 索引建了吗？
   - 查询快吗？

4. **看日志**
   - 有没有报错？
   - 警告信息正常吗？
   - 有没有异常的慢查询？

---

### 跨服务验证方法

LexPrime 有多个服务（后端 API、AI 服务、OCR 服务、合同解析服务等），需要验证服务间的协作。

#### 跨服务验证清单

- [ ] 服务间 API 调用正常
- [ ] 数据格式在服务间传递一致
- [ ] 错误在服务间正确传播和处理
- [ ] 超时和降级逻辑正常
- [ ] 消息队列/事件总线的消息生产消费正常
- [ ] 数据一致性（多个服务的数据不矛盾）

#### 跨服务验证的常见问题

| 问题 | 表现 | 怎么查 |
|---|---|---|
| **数据格式不一致** | 前端传的后端不认，或者后端返回的前端解析错 | 打印完整的请求/响应，对比字段名、数据类型 |
| **服务间超时** | 某个服务慢，拖垮整个流程 | 看每个服务的响应时间，找到瓶颈 |
| **错误处理不一致** | A 服务报错，B 服务收到的是 200 但数据是空的 | 模拟某个服务报错，看其他服务怎么处理 |
| **数据不同步** | 数据库改了，缓存没更；或者一个服务改了，另一个不知道 | 检查数据更新后，相关的缓存/服务有没有同步更新 |

#### 跨服务验证步骤

1. **端到端走一遍完整流程**
   比如：上传合同 → OCR 识别 → AI 解析 → 结果展示
   每一步都检查：数据有没有传过去？格式对不对？结果对不对？

2. **模拟故障场景**
   - 关掉某个服务，看其他服务会不会崩
   - 让某个服务变慢，看会不会超时
   - 让某个服务返回错误，看会不会正确处理

3. **检查数据一致性**
   - 同一个数据在不同服务里是不是一致的？
   - 更新数据后，所有相关的地方都更新了吗？

## 注意事项

### ✅ 应该做的

1. **系统化验证** — 按照清单一项一项来，不要靠感觉
2. **多层次验证** — 单元测试、集成测试、E2E、手动验证，缺一不可
3. **用证据说话** — 拿出测试结果、截图、日志来证明"没问题"
4. **怀疑精神** — 努力去找问题，而不是努力证明没问题
5. **影响面分析** — 想一想改动会影响哪些地方，都去验证一下
6. **写回归测试** — 修了 bug 就加测试，防止以后再犯
7. **记录验证过程** — 你测了什么、怎么测的、结果如何
8. **及时修复发现的问题** — 验证出问题是好事，总比上线后出问题好

### ❌ 不应该做的

1. **不要跳步验证** — 单元测试没过就别测集成，集成没过就别测 E2E
2. **不要自欺欺人** — "应该没问题"、"大概率没事"不算验证
3. **不要只验开心路径** — 边界、异常、错误场景更重要
4. **不要忽略没改的地方** — 回归问题往往出在你觉得"不可能有事"的地方
5. **不要测一次就完事** — 改了代码就要重新验证
6. **不要怕发现问题** — 现在发现问题是成本最低的修复时机
7. **不要把验证推给别人** — 自己写的代码自己先验证好
8. **不要为了赶时间跳过验证** — 省 10 分钟验证，可能花 10 小时救火

## 与其他技能的配合

| 技能 | 关系 | 说明 |
|---|---|---|
| **test-driven-development** | 上游 | TDD 过程中持续写测试，完成前用本技能做整体验证 |
| **systematic-debugging** | 相关 | 调试的第 4 阶段是验证修复，本技能是更全面的完成前验证 |
| **finishing-a-development-branch** | 下游 | 验证通过后，用 finishing 技能做分支收尾 |
| **requesting-code-review** | 并行 | 验证通过后，可以请求代码审查。验证是提交审查前的自检 |
| **receiving-code-review** | 相关 | 审查反馈修改后，用本技能重新验证 |
| **writing-plans** | 上游 | 复杂任务的计划里，应该包含验证计划 |
| **executing-plans** | 并行 | 执行计划的每个步骤，都要做相应的验证 |

```
开发完成
    ↓
verification-before-completion（本技能）
    ↓  验证通过
requesting-code-review
    ↓  审查通过
finishing-a-development-branch
    ↓
合并到 main
```

## 红牌警告

出现以下情况，说明你的验证是不合格的：

- ❌ 你说"应该没问题"，但说不出具体验证了什么
- ❌ 只跑了几个测试，就说"测试都过了"
- ❌ 只测了正常情况，根本没考虑异常和边界
- ❌ 发现了小问题，但觉得"不影响"就放过了
- ❌ 只验证了你改的那几行代码，相关的地方碰都没碰
- ❌ 手动验证就是"点了一下，能用"，根本没深入试
- ❌ 性能差得明显，但你说"功能对了就行"
- ❌ 安全隐患一眼就能看出来，但你说"没人会攻击我们"
- ❌ 验证完了又改了点代码，然后就不重新验证了
- ❌ 你自己都不太敢确定"真的没问题"

> ⚠️ **停下来！** 如果你有以上任何一种情况，说明验证还没做完。回去继续验证，直到你能拍胸脯说"我验证过了，有证据证明它没问题"。
