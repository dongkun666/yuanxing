# Finishing a Development Branch — 完成开发分支

**核心理念（Superpowers）：** 完成不是"写完代码就完了"，而是"验证清楚、决策明确、清理干净、记录完整"。就像离开酒店房间——收拾好东西、关掉灯、检查有没有落下的东西，然后再退房。

> "好的开发流程，开始要有仪式感，结束也要有仪式感。开始时建分支、搭环境、跑基线；结束时做验证、做决策、做清理。" —— Superpowers 工程实践

---

## 何时激活

### 必须激活（强场景）

- 一个功能/修复/重构任务开发完成，准备收尾
- 一个 Plan track 完成，准备进入下一个 track 或集成
- 收到代码审查通过的通知，准备合并
- 实验性改动验证完毕，需要决定保留还是丢弃
- 任何需要"结束当前分支工作"的时刻

### 建议激活（中场景）

- 阶段性暂停工作，准备切换到其他任务
- 一个分支开发了一段时间，需要做一次"期中检查"
- 准备请求代码审查前的自查

### 跳过（弱场景）

- 还在开发中，远未完成
- 只是临时切过去看一眼，马上回来
- 单文件 typo 修复，直接在 main 上改的（不需要走完整流程）

---

## 完整工作流程

```
┌─────────────────┐
│  1. 前置检查     │  ←  不通过 →  回去继续开发
│  （验证清单）    │
└────────┬────────┘
         │ 通过
         ▼
┌─────────────────┐
│  2. 呈现决策选项 │  ←  用户/团队选择
│  （4 种走向）    │
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  3. 执行决策     │
│  （合并/PR/保留/丢弃）│
└────────┬────────┘
         │
         ▼
┌─────────────────┐
│  4. 清理工作     │
│  （worktree/临时文件/文档）│
└─────────────────┘
```

## 第一步：前置检查（验证清单）

在做任何决策之前，必须先完成以下检查。**任何一项不通过，都不能进入决策环节。**

### 1.1 运行测试

**目标：确保所有测试通过，没有回归。**

检查项：
- [ ] 单元测试全部通过
- [ ] 集成测试全部通过（如果有）
- [ ] 端到端测试全部通过（如果有）
- [ ] 新功能有对应的测试覆盖
- [ ] 修复的 bug 有回归测试

**怎么操作：**

```bash
# 根据项目选择对应的命令
npm test              # JavaScript 项目
pytest                # Python 项目
go test ./...         # Go 项目
# ... 其他语言类似
```

**红线：** 带着失败的测试合并，等于把 bug 直接送到生产环境。

---

### 1.2 检查代码质量

**目标：确保代码符合项目规范，没有明显的质量问题。**

检查项：
- [ ] Linter 检查通过，没有 error
- [ ] 代码格式化检查通过
- [ ] 没有遗留的 `console.log` / `print` / `TODO` / `FIXME`
- [ ] 没有注释掉的大段代码
- [ ] 命名清晰，可读性良好
- [ ] 没有硬编码的魔法值（除非有充分理由）

**怎么操作：**

```bash
# 根据项目选择对应的命令
npm run lint          # JavaScript 项目
flake8 / pylint       # Python 项目
go vet                # Go 项目
```

**原则：** 代码质量问题不一定要全部修复，但必须**知道有哪些问题，并且有意识地决定是否接受**。

---

### 1.3 验证功能

**目标：从用户角度确认功能真的能用，而不只是测试通过。**

检查项：
- [ ] 手动验证核心功能路径
- [ ] 验证边界情况（空输入、异常输入、大数据量等）
- [ ] 验证错误处理是否正确
- [ ] 如果有 UI，确认视觉效果符合预期
- [ ] 性能在可接受范围内（如果是性能敏感的改动）

**为什么要手动验证？**
- 测试只能覆盖你想到的场景
- 手动操作能发现"测试没想到但用户一用就出问题"的情况
- 很多 UX 问题只有真正用一下才会发现

---

### 1.4 检查提交历史

**目标：确保提交历史清晰、可追溯、符合规范。**

检查项：
- [ ] 所有改动都已提交，没有未提交的修改
- [ ] 提交信息符合 conventional commit 规范
- [ ] 没有"wip"、"fix"、"update" 这类无意义的提交
- [ ] 提交粒度合理，每个提交做一件事
- [ ] 没有把临时文件、日志、node_modules 等提交进去

**怎么检查：**

```bash
git status              # 确认工作区干净
git log --oneline -20   # 查看最近的提交历史
git diff main..HEAD --stat  # 看看改了哪些文件
```

**如果历史很乱怎么办？**
- 可以用 `git rebase -i` 整理提交历史（squash、reword 等）
- 或者合并成一个清晰的提交（如果团队允许）
- 但要注意：如果已经 push 到远程并且别人也在用，就不要 rebase 了

---

### 前置检查总结

| 检查项 | 不通过怎么办 | 严重程度 |
|---|---|---|
| 测试失败 | 修复测试或修复代码，直到通过 | 🔴 阻塞 |
| Linter 有 error | 修复 error | 🔴 阻塞 |
| 功能验证不通过 | 回去修 bug | 🔴 阻塞 |
| 有未提交的改动 | 提交或 stash | 🟡 必须处理 |
| 提交历史混乱 | 整理提交（如果还没 push） | 🟢 建议优化 |
| 代码有质量问题但能用 | 记录 TODO，后续优化 | 🟢 可以接受 |

**检查完之后，用一句话总结：**
"测试全过了，Linter 干净，功能验证了 3 个核心场景都没问题，提交历史有 5 个 commit 都符合规范，可以进入决策了。"

## 第二步：呈现决策选项

前置检查通过后，**不要自己做决定**，而是把选项清晰地呈现给用户/团队，让他们选择。

### 四个选项

```
┌─────────────────────────────────────────────────────────┐
│                    接下来做什么？                         │
├─────────────┬─────────────┬─────────────┬─────────────┤
│  选项 A     │  选项 B     │  选项 C     │  选项 D     │
│  合并到 main│  创建 PR    │  保留分支    │  丢弃分支    │
└─────────────┴─────────────┴─────────────┴─────────────┘
```

---

### 选项 A：合并到 main（直接合并）

**适用场景：**
- 小改动、低风险
- 已经过充分验证
- 团队允许直接合并（不需要 PR 流程）
- 个人项目或 solo 开发

**操作步骤：**
1. 确保本地 main 是最新的
2. 把特性分支合并到 main
3. 解决可能的冲突
4. 合并后再跑一遍测试（确保合并没引入问题）
5. push 到远程

**命令参考：**

```bash
git checkout main
git pull origin main
git merge <feature-branch>
# 解决冲突（如果有）
npm test / pytest  # 再跑一遍测试
git push origin main
```

**风险提示：**
- 合并后如果发现问题，回滚相对麻烦
- 没有额外的审查环节

---

### 选项 B：创建 PR / MR（请求合并）

**适用场景：**
- 团队有代码审查流程
- 改动较大或较复杂
- 需要别人 review 后再合并
- 公司/项目规定必须走 PR

**操作步骤：**
1. 确保分支已 push 到远程
2. 创建 Pull Request / Merge Request
3. 填写 PR 描述（做了什么、为什么、怎么验证的）
4. 指派 reviewer
5. 等待审查和合并

**PR 描述模板：**

```
## 做了什么
简要描述这个 PR 的内容。

## 为什么要做
背景和动机。

## 怎么验证的
- 测试：运行了哪些测试，结果如何
- 手动验证：验证了哪些场景
- 截图/录屏（如果是 UI 改动）

## 关联的 issue / 计划
Closes #123
关联 Plan: w10-a1

## 风险点
有没有需要特别注意的地方？
```

**优点：**
- 有额外的审查环节，质量更有保障
- 留下了代码审查的记录
- 可以在 PR 里讨论和迭代

---

### 选项 C：保留分支（暂不合并）

**适用场景：**
- 功能做完了，但还没到发布时机
- 需要等其他分支做完一起集成
- 实验性改动，先留着以后再说
- 阶段性完成，先放一放，等有时间再继续

**操作步骤：**
1. 确保所有改动都已提交
2. push 到远程（如果还没 push）
3. 给分支打个 tag 或写个备注，说明当前状态和后续计划
4. 清理 worktree（见第四步）
5. 记录 TODO：什么时候回来继续

**注意事项：**
- 保留的分支要定期 rebase 到最新的 main，避免差距太大
- 不要让"保留"变成"遗忘"——要有明确的后续计划
- 如果一个分支保留了超过 2 周还没动，考虑是不是该丢弃了

---

### 选项 D：丢弃分支（彻底放弃）

**适用场景：**
- 实验失败，方向不对
- 有更好的实现方案，这个分支没用了
- 需求取消了
- 代码写得太烂，与其改不如重写

**操作步骤：**
1. 确认真的不需要了（有没有什么可以 salvage 的代码？）
2. 如果有值得保留的代码片段，先拷出来或记下来
3. 删除本地分支
4. 删除远程分支（如果 push 过）
5. 清理 worktree（见第四步）
6. 记录一下为什么丢弃（避免以后踩同样的坑）

**命令参考：**

```bash
# 删除本地分支
git branch -D <branch-name>

# 删除远程分支
git push origin --delete <branch-name>
```

**心理建设：**
- 丢弃代码不是失败，而是"快速验证了这条路走不通"
- 从失败的分支上学到的东西，和成功的一样有价值
- 关键是要**知道为什么失败**，下次不要犯同样的错误

---

## 第三步：执行决策

根据选择的选项，执行对应的操作。这一步的关键是：**做完之后验证一下。**

### 合并后验证

如果选择了合并到 main：
- [ ] 合并后所有测试仍然通过
- [ ] 手动验证核心功能正常
- [ ] main 分支状态干净
- [ ] 远程 main 已更新

### PR 创建后验证

如果选择了创建 PR：
- [ ] PR 已成功创建
- [ ] 描述清晰完整
- [ ] CI 检查通过（如果有）
- [ ] reviewer 已指派

### 保留分支验证

如果选择了保留：
- [ ] 所有改动都已提交和 push
- [ ] 有明确的后续计划和时间点
- [ ] 记录了当前状态

### 丢弃分支验证

如果选择了丢弃：
- [ ] 本地分支已删除
- [ ] 远程分支已删除（如果有）
- [ ] 有价值的代码片段已保存（如果需要）
- [ ] 记录了丢弃原因

---

## 第四步：清理工作

**Superpowers 原则：** 用完的东西要收拾干净，不要留下垃圾。

### 4.1 删除 Worktree

如果是用 `git worktree` 开发的，任务完成后一定要清理。

**怎么删：**

```bash
# 先回到主工作区
cd /path/to/main

# 列出所有 worktree，确认要删的那个
git worktree list

# 删除 worktree
git worktree remove .worktrees/<branch-name>
```

**如果有未提交的改动：**
- 确定要丢弃的话：`git worktree remove -f .worktrees/<branch-name>`
- 不确定的话：先回去提交或 stash，再删

**为什么不能直接 `rm -rf`：**
- 直接删目录会在 git 里留下无效的 worktree 引用
- 正确的做法是用 `git worktree remove`
- 如果不小心手动删了，用 `git worktree prune` 清理引用

---

### 4.2 清理临时文件

开发过程中可能产生的临时文件：

| 类型 | 示例 | 怎么清理 |
|---|---|---|
| 日志文件 | `*.log`、`debug.log` | 直接删掉 |
| 临时数据 | `tmp/`、`temp/` | 直接删掉 |
| 构建产物 | `dist/`、`build/`、`__pycache__/` | 通常在 .gitignore 里，不用管，但也可以清 |
| 测试输出 | `coverage/`、`.pytest_cache/` | 可以删掉 |
| 调试用的代码 | 注释掉的代码、`console.log` | 提交前就该清掉 |

**检查命令：**

```bash
# 看看有没有未跟踪的文件
git status

# 列出所有未跟踪的文件
git ls-files --others --exclude-standard
```

**原则：**
- 如果是在 .gitignore 里的文件，无所谓，留着也行
- 如果是不小心产生的、不该存在的文件，删掉
- 如果不确定是什么文件，先看看内容再决定

---

### 4.3 更新文档

**Superpowers 理念：** 代码写完了，文档也要跟上。不然三个月后谁也不知道这东西是干嘛的。

需要检查的文档：

| 文档类型 | 什么时候需要更新 |
|---|---|
| README | 新增了功能、改变了使用方式 |
| API 文档 | 新增或修改了 API |
| 架构文档 | 改变了架构设计 |
| 部署文档 | 改变了部署方式或依赖 |
| Plan / Final Report | 完成了一个 Plan track |
| CHANGELOG | 值得记录的变更 |
| 代码注释 | 复杂的逻辑需要解释 |

**最低要求：**
- 至少更新一下 Plan 的 Final Report（如果是在做 Plan）
- 如果有对外的 API，至少更新 API 文档
- 如果连文档都懒得写，至少在 commit message 里写清楚

## LexPrime 项目适配

### 分支命名回顾

```
w<周数>-<track编号>-<简短描述>
```

示例：
- `w10-a1-frontend-auth-reconnect`
- `w9-b3-backend-contract-ocr`
- `w8-c2-ai-service-prompt-tuning`

完成分支时，根据命名就能快速知道这个分支属于哪个 Plan、哪个 Track。

---

### LexPrime 提交流程

LexPrime 项目的标准提交流程：

```
开发完成
    ↓
前置检查（测试 + Lint + 功能验证）
    ↓
整理提交历史（rebase -i，确保符合 conventional commit）
    ↓
请求代码审查（requesting-code-review skill）
    ↓
处理审查反馈（receiving-code-review skill）
    ↓
审查通过 → 合并到 main
    ↓
清理 worktree + 更新 Plan Final Report
```

---

### Plan Final Report 更新

完成一个 track 后，必须更新对应的 Plan Final Report：

**Final Report 应该包含：**
1. 完成了什么（功能列表）
2. 怎么验证的（测试结果、手动验证场景）
3. 遇到了什么问题，怎么解决的
4. 有没有遗留的 TODO 或技术债务
5. 改动了哪些文件 / 模块
6. 提交历史概览

**位置：** `docs/plans/w<N>/final-report.md` 或对应的 track 目录

---

### LexPrime 合并策略

LexPrime 项目推荐使用 **Squash Merge** 或 **Rebase Merge**，保持 main 分支历史干净：

- **Squash Merge：** 把整个分支的所有提交合并成一个提交 → main 历史最干净
- **Rebase Merge：** 把分支的提交 rebase 到 main 上 → 保留提交细节，历史线性
- **不推荐普通 Merge：** 会产生很多 merge commit，历史看起来乱

**选择建议：**
- 小功能 / bugfix → Squash Merge（一个清晰的提交）
- 大功能 / 多个独立步骤 → Rebase Merge（保留每个步骤的提交）

## 注意事项与陷阱

### ❌ 常见错误

#### 1. 跳过验证直接合并

**表现：** "我觉得没问题"、"应该能过"、"先合了再说"

**后果：**
- 把 bug 带到 main
- 影响其他开发人员
- 回滚成本很高

**正确做法：** 按照检查清单一项一项来，不要跳步。

---

#### 2. 不清理 worktree，越积越多

**表现：** `.worktrees/` 目录下有十几个早就做完的分支

**后果：**
- 占用磁盘空间
- 搞不清哪个是哪个
- 想删的时候又不敢删，怕删错了

**正确做法：** 任务完成立刻清理，养成习惯。

---

#### 3. 合并后忘了 push

**表现：** 本地 main 已经合并了，但远程还是旧的

**后果：**
- 其他人 pull 不到最新的
- 你自己在另一台机器上也看不到
- 等于白合并了

**正确做法：** 合并完就 push，然后确认一下。

---

#### 4. 丢弃分支时把有用的代码也丢了

**表现：** 整个分支全删了，过了两周又想起来"哎那个分支里有段代码还能用"

**后果：**
- 找不回来了（除非翻 reflog，但很麻烦）
- 又要重写一遍

**正确做法：** 丢弃前先看看，有价值的代码片段先拷出来。

---

#### 5. 保留的分支变成"僵尸分支"

**表现：** 说好了"以后再继续"，结果半年过去了还在那放着

**后果：**
- 和 main 差距越来越大，再想合并比登天还难
- 占着坑，让人以为还有人在做
- 最后还是得删

**正确做法：**
- 保留时设定一个明确的"过期时间"
- 超过时间还没动，就果断丢弃
- 与其让它烂着，不如删了干净

---

### ✅ 最佳实践

1. **检查清单化** — 把前置检查做成清单，一项一项打勾，不要靠记忆
2. **决策透明化** — 把选项摆出来，让团队/用户做选择，不要自己拍脑袋
3. **清理自动化** — 能自动清理的就自动清理，减少手动操作
4. **文档同步化** — 代码写完了，文档也同步更新，不要攒到"以后"
5. **完成有仪式感** — 完成一个分支是值得庆祝的小事，给自己一点正反馈

## 与其他技能的配合

| 技能 | 关系 | 说明 |
|---|---|---|
| **`using-git-worktrees`** | 上游 | 在 worktree 里开发 → 开发完用本技能收尾 |
| **`requesting-code-review`** | 并行 | 前置检查通过后，可以请求代码审查 |
| **`receiving-code-review`** | 并行 | 收到审查反馈并处理完后，用本技能继续收尾 |
| **`test-driven-development`** | 上游 | TDD 开发完的代码，用本技能做收尾 |
| **`git-commit`** | 辅助 | 提交阶段用 git-commit，收尾阶段用本技能 |
| **`writing-plans`** | 相关 | 完成 Plan track 后，更新 plan 文档 |
| **`brainstorming`** | 相关 | 丢弃分支后，可以 brainstorm 新的方向 |

## 红牌警告

以下行为是绝对禁止的，一旦出现就是严重问题：

- ❌ **带着失败的测试合并** — 明知测试挂了还合，等于主动引入 bug
- ❌ **不做任何验证就合并** — "我觉得没问题"不是验证
- ❌ **合并后不跑测试** — 合并冲突可能引入新问题
- ❌ **用完 worktree 不清理** — 懒不是理由，这是基本素养
- ❌ **丢弃分支前不看内容** — 万一有有用的东西呢？
- ❌ **只写代码不写文档** — 三个月后你自己都看不懂
- ❌ **自己偷偷合并，不告诉任何人** — 团队协作要有透明度
