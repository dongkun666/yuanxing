# Test-Driven Development — 测试驱动开发

**核心理念：** 先写测试，再写实现。通过 RED → GREEN → REFACTOR 循环，让测试引导设计，确保每一行代码都有存在的理由。

> "测试不是为了发现 bug，而是为了驱动设计。" —— Kent Beck

---

## 何时激活

### 必须激活（强场景）

- 开发新功能或新模块（无论大小）
- 重构现有代码（任何范围的重构）
- 修复 bug（先写测试复现 bug，再修复）
- 实现算法或核心业务逻辑
- 用户明确说"用 TDD"、"先写测试"、"测试驱动"
- 任何你希望代码有可靠测试覆盖的场景

### 建议激活（中场景）

- 修改已有功能（先确保现有测试通过，再添加新测试）
- 修复复杂 bug（涉及多个模块或逻辑路径）
- 你对代码正确性没有十足把握时
- 需要长期维护的代码

### 跳过（弱场景）

- 纯探索性代码（throwaway code，用完就扔）
- 简单的配置修改或文档更新
- 原型/概念验证（PoC）且明确说"先跑起来再说"
- 用户明确要求"不用写测试"、"先实现再说"（但事后要补）

## RED-GREEN-REFACTOR 循环详解

TDD 的核心是三个阶段的无限循环。**每一轮循环都应该很小**，通常 5-10 分钟完成一轮。

```
┌──────────┐     ┌──────────┐     ┌────────────┐
│   RED    │────▶│  GREEN   │────▶│ REFACTOR   │
│  (红)    │     │  (绿)    │     │  (重构)    │
└──────────┘     └──────────┘     └────────────┘
      ▲                                       │
      └───────────────────────────────────────┘
```

---

### 第一阶段：RED（红）—— 写一个失败的测试

**目标：** 写一个测试，它描述了你想要的行为，然后看着它失败。

#### 步骤

1. **写测试** — 针对你即将实现的功能，写一个测试用例
2. **确保测试编译/运行** — 测试本身应该是可执行的
3. **看着它失败** — 运行测试，确认它是失败的（红色）

#### 为什么这一步很重要？

- **验证测试的有效性** — 如果测试从不失败，那它可能什么都没测
- **明确需求** — 测试就是可执行的需求规格
- **防止自欺欺人** — 避免写了"看起来对"但其实没被验证的代码

#### 怎么做才对？

✅ **从最简单的测试开始** — 比如空输入、边界情况、最基础的场景
✅ **测试行为，不是实现** — 测"做了什么"，不测"怎么做的"
✅ **一次只写一个测试** — 不要一口气写一堆测试
✅ **给测试起个好名字** — 从名字就能看出测的是什么场景

#### RED 阶段的检查清单

- [ ] 测试代码能编译/运行吗？
- [ ] 测试失败了吗？（不是语法错误，是断言失败）
- [ ] 失败信息清晰吗？能看出为什么失败吗？
- [ ] 这个测试真的在测你想测的东西吗？

> ⚠️ **重要：** 在 RED 阶段，**绝对不要写实现代码**。如果你发现自己"顺便"写了点实现代码，停下来，删掉它，先让测试失败。

---

### 第二阶段：GREEN（绿）—— 写最少的代码让测试通过

**目标：** 用最快、最简单、甚至"丑陋"的方式，让测试变成绿色。

#### 步骤

1. **写最少的实现代码** — 刚好让测试通过就行
2. **运行测试** — 确认它变绿了
3. **停手** — 不要多写一行代码

#### 为什么"最少的代码"很重要？

- **避免过度设计** — 你以为需要的，测试可能根本不需要
- **保持专注** — 一次只解决一个问题
- **让重构有意义** — 如果代码已经很"完美"，你还会重构吗？

#### "最少"到什么程度？

可以很"无耻"：

```python
# 测试
def test_add():
    assert add(2, 3) == 5

# GREEN 阶段的实现 — 可以这么简单！
def add(a, b):
    return 5  # 硬编码！
```

没错，硬编码都是可以的。下一个测试会逼你写出真正的实现。

#### 怎么做才对？

✅ **怎么简单怎么来** — 硬编码、复制粘贴、if-else 堆砌，都可以
✅ **只要能通过测试就行** — 不要考虑"优雅"、"可维护"，那是重构阶段的事
✅ **越快越好** — 争取在 2 分钟内从红到绿
✅ **如果卡住了，说明测试写大了** — 把测试拆小一点

#### GREEN 阶段的检查清单

- [ ] 所有测试都通过了吗？（不只是刚才那个）
- [ ] 你写的代码是不是最少的？有没有多余的？
- [ ] 有没有"顺便"加了测试没要求的功能？（有的话删掉）

---

### 第三阶段：REFACTOR（重构）—— 在保持测试通过的前提下改进代码

**目标：** 现在测试是你的安全网，大胆地优化代码结构、消除重复、提升可读性。

#### 步骤

1. **审视代码** — 看看哪里有味道：重复、命名不好、结构混乱...
2. **小步重构** — 每次只改一点，改完就运行测试
3. **确保测试一直绿着** — 如果变红了，撤销刚才的改动，换个方式

#### 重构什么？

| 重构类型 | 示例 |
|---|---|
| **消除重复** | 提取公共函数、合并相似逻辑 |
| **改善命名** | 把 `f()` 改成 `calculate_total()` |
| **简化逻辑** | 把嵌套的 if-else 改成卫语句 |
| **拆分函数/类** | 把一个 50 行的函数拆成 3 个小函数 |
| **改善数据结构** | 用合适的数据结构替代临时变量 |
| **消除魔法值** | 把硬编码的数字变成有名字的常量 |

#### 怎么做才对？

✅ **小步前进** — 每改一点就运行一次测试，确保没破坏东西
✅ **每次只做一种重构** — 不要一边重命名一边改逻辑
✅ **测试本身也可以重构** — 测试代码也是代码，也要保持整洁
✅ **重构完了就停** — 不要为了"更优雅"而无限重构

#### REFACTOR 阶段的检查清单

- [ ] 所有测试仍然通过吗？
- [ ] 代码比之前更清晰了吗？
- [ ] 有没有重复代码被消除？
- [ ] 你有没有改变外部行为？（不应该改变）
- [ ] 测试代码本身是不是也需要清理？

---

### 循环节奏

**一轮循环应该多长？**

| 阶段 | 建议时长 |
|---|---|
| RED | 1-3 分钟 |
| GREEN | 1-3 分钟 |
| REFACTOR | 2-5 分钟 |
| **一轮总计** | **5-10 分钟** |

如果一轮超过 15 分钟，说明：
- 测试写太大了 → 拆成更小的测试
- 你想多了 → 先让它通过，再考虑优雅
- 问题比想象的复杂 → 退一步，找个更小的切入点

> 💡 **经验法则：** 如果你在 GREEN 阶段卡了超过 5 分钟，说明测试太大了。删掉当前测试，写一个更小的。

## TDD 的三条法则

Robert C. Martin（Uncle Bob）提出的 TDD 三定律：

1. **在编写不能通过的单元测试前，不可编写生产代码**
2. **只可编写刚好无法通过的单元测试，不能编译也算不通过**
3. **只可编写刚好足以通过当前失败测试的生产代码**

这三条法则确保了：
- 每一行生产代码都被测试覆盖
- 你不会写多余的代码
- 测试始终领先于实现

## 测试反模式参考

### ❌ 反模式 1：先写实现，后补测试

**表现：** 代码写完了，再补测试"意思意思"。

**问题：**
- 测试是为了"覆盖"而写，不是为了驱动设计
- 你会下意识地写"能通过"的测试，而不是"有意义"的测试
- 测试发现不了设计问题，因为设计已经定了

**纠正：** 删掉实现代码，从测试开始重来。

---

### ❌ 反模式 2：测试写得太大

**表现：** 一个测试测十几个场景，RED 阶段花半小时，GREEN 阶段又花半小时。

**问题：**
- 失去了 TDD 的节奏感
- 失败时不知道具体哪里错了
- 容易卡住，打击信心

**纠正：** 把大测试拆成小测试，一个场景一个测试。

---

### ❌ 反模式 3：跳过重构

**表现：** 测试一变绿就马上写下一个测试，从不整理代码。

**问题：**
- 代码越来越乱，技术债务越积越多
- 到最后你自己都不想看自己的代码
- 测试越写越慢，因为代码太难用了

**纠正：** 每一轮都花 2-5 分钟重构，养成习惯。

---

### ❌ 反模式 4：测试实现细节

**表现：** 测试断言内部变量的值、mock 内部函数调用、甚至直接测私有方法。

**问题：**
- 重构会破坏测试（即使行为没变）
- 测试和实现耦合太紧，改代码的成本很高
- 测试失去了"安全网"的意义，变成了"绊脚石"

**纠正：** 测试行为（输入输出），不测实现细节。

---

### ❌ 反模式 5：过度 mock

**表现：** 什么都 mock，测试里全是 mock 代码，真正的逻辑没几行。

**问题：**
- 测试和真实世界脱节，通过了测试但实际可能有问题
- mock 成本很高，写测试变成了折磨
- 重构时 mock 也要跟着改，维护成本巨大

**纠正：** 能不 mock 就不 mock，优先用真实对象。只 mock 真正的外部依赖（数据库、网络等）。

---

### ❌ 反模式 6：测试之间有依赖

**表现：** 测试 B 依赖测试 A 的执行结果，必须按顺序跑。

**问题：**
- 单独跑某个测试会失败
- 测试顺序变了结果就不一样
- 很难定位问题

**纠正：** 每个测试都应该是独立的，自己准备数据，自己清理现场。

---

### ❌ 反模式 7：断言过于宽松

**表现：** 只断言"不抛异常"、"返回不是 null"，不测具体值。

**问题：**
- 测试几乎没有防护力
- 代码逻辑错了测试也可能通过

**纠正：** 断言具体的、有意义的值。

---

## 常见误区

### 误区 1："TDD 太慢了"

**真相：** 短期看，写测试确实多花了时间；但长期看，TDD 节省的时间远多于投入：
- 减少调试时间（bug 刚写出来就被测试抓住了）
- 减少回归问题（有测试保护，改代码不怕）
- 更好的设计（测试驱动的设计往往更简洁、更解耦）
- 更少的技术债务（每轮都重构，代码始终整洁）

---

### 误区 2："简单的代码不用写测试"

**真相：**
- 简单的代码也可能写错
- 今天简单，明天可能变复杂
- 简单的测试写起来也简单，成本很低
- 有测试的代码，改起来更放心

---

### 误区 3："TDD 就是单元测试"

**真相：** TDD 是一种**设计方法**，单元测试只是工具。TDD 的核心价值在于：
- 让你从使用者的角度思考 API 设计
- 逼迫你把问题拆小
- 给你重构的勇气
- 提供活的文档

单元测试是副产品，不是目标。

---

### 误区 4："测试覆盖率 100% 就安全了"

**真相：** 覆盖率只是一个指标，不代表测试质量：
- 100% 覆盖但没有断言的测试，毫无意义
- 测错了东西，覆盖率再高也没用
- 覆盖率低不代表测试不好（但通常是个警告信号）

追求**有意义的测试**，而不是追求覆盖率数字。

---

### 误区 5："重构就是重写"

**真相：** 重构是**在不改变外部行为的前提下改善内部结构**。
- 重构时测试应该一直通过
- 如果改了行为，那不是重构，是重写
- 重写也可以，但要明确知道你在做什么

## LexPrime 项目适配

LexPrime 项目包含 Python 后端和 JavaScript 前端，需要分别处理。

### Python 部分：pytest

#### 测试文件位置约定

```
项目根目录/
├── src/
│   └── lex_prime/
│       ├── module.py          # 实现代码
│       └── ...
└── tests/
    ├── test_module.py         # 测试代码（和源码对应）
    ├── conftest.py            # pytest 配置和 fixtures
    └── ...
```

#### 测试命名规范

- 测试文件：`test_*.py` 或 `*_test.py`
- 测试类：`Test*`（如果用类的话）
- 测试函数：`test_*`
- 测试名要描述场景：`test_xxx_when_yyy`、`test_xxx_should_yyy`

✅ 好名字：
```python
def test_add_two_positive_numbers():
def test_divide_by_zero_raises_error():
def test_empty_list_returns_zero():
```

❌ 坏名字：
```python
def test_add():        # 太模糊，什么场景？
def test_func1():      # 根本不知道测什么
def test_case1():      # case1 是什么？
```

#### pytest 常用技巧

**基本断言：**
```python
assert result == expected
assert result is not None
assert isinstance(result, int)
```

**断言异常：**
```python
import pytest

def test_divide_by_zero():
    with pytest.raises(ZeroDivisionError):
        divide(1, 0)
```

**参数化测试：**
```python
import pytest

@pytest.mark.parametrize("a, b, expected", [
    (2, 3, 5),
    (0, 0, 0),
    (-1, 1, 0),
    (100, 200, 300),
])
def test_add(a, b, expected):
    assert add(a, b) == expected
```

**fixtures：**
```python
import pytest

@pytest.fixture
def sample_data():
    return {"name": "test", "value": 42}

def test_something(sample_data):
    assert sample_data["value"] == 42
```

#### 运行测试

```bash
# 运行所有测试
pytest

# 运行指定文件
pytest tests/test_module.py

# 运行指定测试函数
pytest tests/test_module.py::test_function_name

# 运行时显示 print 输出
pytest -s

# 只运行失败的测试
pytest --lf

# 显示覆盖率
pytest --cov=src
```

✅ 好名字：

test('adds two positive numbers correctly', () => { ... })

```javascript
import { add } from './utils'

describe('add', () => {
  test('adds two numbers', () => {
    expect(add(2, 3)).toBe(5)
  })

  test('handles zero', () => {
    expect(add(0, 0)).toBe(0)
  })

```

#### 常用断言

```javascript
// 相等

// 布尔
expect(result).toBeTruthy()
expect(result).toBeFalsy()
expect(result).toBeNull()
expect(result).toBeUndefined()

// 包含
expect(array).toContain(item)
expect(string).toMatch(/pattern/)

// 异常
expect(() => fn()).toThrow()
expect(() => fn()).toThrow(ErrorType)
```

#### 参数化测试

```javascript
test.each([
  [2, 3, 5],
  [0, 0, 0],
  [-1, 1, 0],

  expect(add(a, b)).toBe(expected)
})
```

## 注意事项

### ✅ 应该做的

1. **小步前进** — 测试要小，实现要少，重构要勤
2. **先写测试** — 严格遵守 RED → GREEN → REFACTOR 顺序
3. **每轮都重构** — 不要把重构攒到"以后"，以后就是永远
4. **测试行为** — 测"做什么"，不测"怎么做"
5. **保持测试独立** — 每个测试自己准备、自己清理
6. **给测试起好名字** — 看到名字就知道测什么
7. **经常运行测试** — 改一点就跑一次，保持绿灯
8. **勇敢地删代码** — 如果测试不需要，就删掉

### ❌ 不应该做的

1. **不要先写实现后补测试** — 那不是 TDD
2. **不要写太大的测试** — 拆小，再拆小
3. **不要跳过 RED 阶段** — 确保测试真的会失败
4. **不要在 GREEN 阶段"顺便"加功能** — 多余的代码就是债务
5. **不要跳过重构** — 技术债务会利滚利
6. **不要测试实现细节** — 重构会破坏它们
7. **不要过度 mock** — 能不用 mock 就不用
8. **不要追求 100% 覆盖率** — 追求有意义的测试

## 删除测试前写的代码

这是 Superpowers TDD 的一条铁律：

> 如果在写测试之前你已经写了实现代码，**删掉实现代码，从测试开始**。

### 为什么这么严格？

1. **打破惯性** — 如果你已经写了实现，再写测试时会下意识地"配合"实现，而不是思考真正需要什么
2. **验证测试的价值** — 如果删掉实现后你写不出测试来，说明你根本不知道自己要做什么
3. **训练思维方式** — TDD 是一种思维习惯，需要严格训练才能养成

### 怎么做？

1. 停下来，承认你抢先了
2. 把你写的实现代码**删掉**（或者注释掉，但删掉更彻底）
3. 从测试开始，重新走 RED → GREEN → REFACTOR 循环
4. 你会发现，重新写出来的代码，比之前的更好

> 💡 **心理建设：** 删代码不是浪费，是投资。你花 5 分钟删掉重写，省下的是以后几小时的调试和返工。

## 与其他技能的配合

| 技能 | 关系 | 说明 |
|---|---|---|
| **writing-plans** | 前置 | 复杂任务先做计划，再用 TDD 逐步实现 |
| **brainstorming** | 前置 | 需求不明确时先 brainstorm，再 TDD |
| **requesting-code-review** | 下游 | TDD 完成后，用 code review 做最终检查 |
| **git-commit** | 并行 | 每轮 TDD 循环（或几轮后）做一次提交 |
| **using-git-worktrees** | 辅助 | 多分支并行开发时，保持测试环境干净 |

## 红牌警告

出现以下情况，说明你可能偏离了 TDD 的轨道：

- ❌ 你已经写了 100 行实现代码，但一行测试都没写
- ❌ 测试"总是通过"，你不记得上次看到红色是什么时候
- ❌ 一个测试文件有 500 行，一个测试函数测了 10 个场景
- ❌ 你在测试里 mock 了 80% 的东西
- ❌ 重构时测试全红了，你不知道哪里错了
- ❌ 你说"这个太简单了，不用写测试"
- ❌ 你说"先实现，以后再补测试"
- ❌ 测试覆盖率很高，但你对代码质量还是没信心
