# Executing Plans — 执行计划

**核心理念：批量执行 + 检查点 + 即时验证。** 不盲目一口气跑完所有任务，而是分批推进，每完成一小批就停下来检查，确保方向正确、质量达标后再继续。

> "一步一步来，一步都不能错。" —— 沃纳·冯·布劳恩

## 何时激活

**必须激活（强场景）：**

- 已有明确的任务计划（来自 `writing-plans` 或其他规划），需要按顺序执行
- 涉及 3 个或更多任务的开发工作
- 跨文件、跨模块的功能实现或重构
- 用户明确要求"按计划执行"、"分步来"、"做完一批检查一下"
- 高风险变更（涉及核心逻辑、数据结构、对外接口）

**建议激活（中场景）：**

- 任务列表较长，需要合理控制节奏
- 需要向用户同步进度的协作场景
- 新人或不熟悉的代码域，边做边验证
- 预计执行时间超过 15 分钟的任务

**跳过（弱场景）：**

- 单任务、单文件、简单修改（< 50 行）
- 纯文档更新或 typo 修复
- 用户明确说"一次性做完"、"不用停，直接搞完"
- 紧急热修复且影响范围已确认

---

## 工作流程

采用 **分批执行 + 检查点** 模型，确保每一步都扎实可靠。

```
┌─────────────────────────────────────────────────────────────┐
│                        完整计划                               │
│  [任务1] [任务2] [任务3] [任务4] [任务5] [任务6] [任务7] ...  │
└───────────────┬───────────────────┬───────────────────┬─────┘
                │                   │                   │
                ▼                   ▼                   ▼
         ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
         │   第一批      │     │   第二批      │     │   第三批      │
         │  任务1-2-3   │     │  任务4-5-6   │     │   任务7...  │
         └──────┬──────┘     └──────┬──────┘     └──────┬──────┘
                │                   │                   │
                ▼                   ▼                   ▼
         ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
         │  人工检查点   │────▶│  人工检查点   │────▶│  人工检查点   │
         │  (验证+确认)  │     │  (验证+确认)  │     │  (验证+确认)  │
         └─────────────┘     └─────────────┘     └─────────────┘
```

### 核心原则

1. **每批 2-3 个任务** —— 不多不少，既能保持节奏，又足够小以便及时发现问题
2. **每个任务执行后立即验证** —— 不攒到批结束，发现问题立刻定位
3. **每批结束后人工检查点** —— 停下来，向用户汇报，确认没问题再继续
4. **遇到问题立即停止** —— 绝不带着问题往下走，及时沟通、及时调整

## 执行模式

### 模式一：单步模式（Step-by-Step）

**适用场景：** 高风险、高不确定性、用户希望全程把控

**特点：**
- 每个任务执行前都告知用户
- 每个任务完成后都汇报结果
- 每个任务都等待用户确认后再继续

**流程：**
```
告知任务X → 执行任务X → 验证任务X → 汇报结果 → 用户确认 → 任务X+1
```

**何时选用：**
- 涉及生产环境或核心数据
- 用户第一次合作，建立信任阶段
- 方案还在探索中，可能随时调整
- 任务之间依赖关系复杂

---

### 模式二：批量模式（Batch Mode）⭐ 推荐默认

**适用场景：** 计划已确认、风险可控、追求效率

**特点：**
- 每批 2-3 个任务连续执行
- 每个任务内部自行验证
- 整批完成后统一汇报，等待用户确认
- 用户确认后再开始下一批

**流程：**
```
┌───────────────────────────────┐
│  第 N 批（任务 X, X+1, X+2）   │
│                               │
│  执行X → 验证X → 执行X+1 → ... │
└───────────────┬───────────────┘
                │
                ▼
         汇报本批成果
         （完成了什么、验证结果、遇到的问题）
                │
                ▼
         用户确认 / 调整
                │
                ▼
         第 N+1 批...
```

**批大小选择指南：**

| 批大小 | 适用场景 | 优点 | 缺点 |
|--------|----------|------|------|
| **2 个/批** | 中等风险、任务较复杂 | 反馈更快，问题更早暴露 | 节奏稍慢 |
| **3 个/批** ⭐ | 常规任务、计划已确认 | 效率与安全的平衡 | 标准选择 |
| **> 3 个/批** | 极低风险、机械性任务 | 效率高 | 问题可能累积 |

> 💡 **经验法则：** 不确定的时候选 2 个/批。觉得稳了再升到 3 个/批。永远不要超过 3 个/批。

## 详细执行步骤

### 第一步：执行前准备

1. **回顾计划** —— 再看一遍任务列表，确保理解每个任务的目标和依赖
2. **确认起始状态** —— 代码库干净、依赖已安装、测试能跑通
3. **告知用户** —— "我要开始执行了，先做第 1 批（任务 1-3），做完跟你汇报"

### 第二步：单个任务执行循环

对每个任务，遵循以下子流程：

```
┌─────────────┐
│  1. 理解任务  │  再读一遍任务描述，确认目标
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  2. 执行任务  │  按计划编写/修改代码
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  3. 验证任务  │  运行任务指定的验证步骤
└──────┬──────┘
       │
       ▼
┌─────────────┐
│  4. 记录结果  │  成功/失败、验证输出、遇到的问题
└──────┬──────┘
       │
       ├─ 成功 → 继续下一个任务
       │
       └─ 失败 → 进入异常处理流程（见下文）
```

### 第三步：批次结束汇报

每批任务完成后，向用户提交清晰的汇报：

**汇报模板：**
```
## 第 X 批完成汇报

**完成任务：**
- ✅ 任务 1：[任务标题] — 验证通过
- ✅ 任务 2：[任务标题] — 验证通过
- ⚠️ 任务 3：[任务标题] — [说明情况]

**本批成果：**
- 修改了哪些文件
- 实现了什么功能
- 验证结果摘要

**注意事项 / 调整：**
- 执行中做了哪些微调（为什么）
- 有没有偏离计划的地方

**下一步：**
- 下一批准备做任务 X-Y
- 还是需要先讨论一下？

你看这批没问题吧？我们继续下一批吗？
```

### 第四步：人工检查点

用户确认后才能继续下一批。检查点的目的：

1. **质量把关** —— 人眼检查一遍，AI 可能注意不到的问题
2. **方向校准** —— 有没有跑偏？是不是用户想要的？
3. **节奏调整** —— 太快了？太慢了？需要调整批大小吗？
4. **计划更新** —— 基于已完成的情况，后续任务需要调整吗？

## 验证清单

每个任务完成后，必须通过以下验证（根据任务类型选用）：

### 代码质量验证

- [ ] **编译/类型检查通过** —— `tsc --noEmit` / `cargo check` / `go build` 等
- [ ] **Lint 通过** —— 没有新增 lint 错误
- [ ] **相关单元测试通过** —— 运行任务涉及的测试文件
- [ ] **没有引入新的警告** —— 编译警告、deprecation 警告等

### 功能验证

- [ ] **核心功能正常** —— 按任务描述的功能点逐一验证
- [ ] **边界情况处理** —— 空值、异常输入、极端值
- [ ] **错误处理生效** —— 出错时有合理的提示和降级
- [ ] **与现有代码兼容** —— 没有破坏已有功能

### 集成验证

- [ ] **端到端流程跑通** —— 如果涉及多个模块，完整走一遍
- [ ] **API 接口符合预期** —— 请求/响应格式正确
- [ ] **数据迁移成功** —— （如涉及）数据库 schema 变更正确
- [ ] **配置更新生效** —— （如涉及）新配置项正常工作

### 提交前验证

- [ ] **diff 检查** —— 只改了该改的，没有意外变更
- [ ] **没有遗留的调试代码** —— `console.log`、`debugger`、`print` 等
- [ ] **注释和文档更新** —— 代码变更了，对应文档也要更
- [ ] **命名一致** —— 变量名、函数名遵循项目规范

> ⚠️ **重要：** 验证不通过 = 任务未完成。绝不能把有问题的任务带入下一批。

## 异常处理

### 任务失败时的处理流程

```
任务执行 / 验证失败
        │
        ▼
┌─────────────────────────┐
│  1. 立即停止，不要继续   │  🔴 绝对不要跳过问题往下走
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│  2. 收集失败信息         │
│     - 错误信息和栈追踪   │
│     - 复现步骤           │
│     - 相关代码位置       │
└───────────┬─────────────┘
            │
            ▼
┌─────────────────────────┐
│  3. 初步分析原因         │  🧐 尝试定位问题（5-10分钟）
│     - 是我的问题吗？     │
│     - 是计划的问题吗？   │
│     - 是环境的问题吗？   │
└───────────┬─────────────┘
            │
            ├─ 能快速修复（<5分钟）且有把握 ──┐
            │                               │
            ▼                               ▼
┌─────────────────────────┐       ┌─────────────────────────┐
│  4a. 修复并重新验证      │       │  4b. 停止并向用户汇报    │
│     - 说明改了什么       │       │     - 描述问题现象       │
│     - 说明为什么这么改   │       │     - 你分析的可能原因   │
│     - 重新验证通过       │       │     - 你建议的解决方案   │
└───────────┬─────────────┘       │     - 等待用户决策       │
            │                     └─────────────────────────┘
            ▼
    继续后续任务
```

### 常见异常类型及应对

| 异常类型 | 表现 | 应对策略 |
|----------|------|----------|
| **计划错误** | 计划中的代码与实际代码库不匹配 | 停下来，说明差异，提议调整计划 |
| **依赖缺失** | 缺少库、环境不对、版本不兼容 | 先确认是否可以安装/升级，再行动 |
| **测试失败** | 现有测试挂了 | 先搞清楚是改坏了还是测试本来就有问题 |
| **理解偏差** | 做出来的和用户想的不一样 | 立即停止，澄清需求，调整方向 |
| **范围蔓延** | 做着做着发现还要改好多东西 | 停下来，评估影响，和用户讨论是否纳入 |
| **阻塞问题** | 遇到完全没思路的问题 | 如实告知，请求帮助，不要硬扛 |

### 异常汇报模板

```
## ⚠️ 执行遇到问题

**任务：** [任务编号和标题]

**问题现象：**
[简明描述哪里出错了]

**错误信息：**
```
[粘贴关键错误信息]
```

**我的分析：**
- 可能的原因 1：...

**建议方案：**
方案 A：[描述] — 优点 / 缺点
方案 B：[描述] — 优点 /缺点

你觉得怎么处理比较好？或者你有其他想法？
```

## 注意事项与最佳实践

### ✅ 应该做的

1. **严格按计划执行** —— 计划是双方确认的，不要随意加戏
2. **每个任务都验证** —— 不要嫌麻烦，验证是质量的底线
3. **每批都停下来确认** —— 不要一口气跑完全部，那是赌运气
4. **如实汇报进度** —— 成了就说成了，有问题就说有问题
5. **记录变更和调整** —— 实际执行和计划不一样的地方，记下来并说明原因
6. **保持沟通节奏** —— 让用户知道你在干嘛、做到哪了
7. **遇到问题早说** —— 越早说，成本越低，不要等到攒成大问题

### ❌ 不应该做的

1. **跳过验证** —— "应该没问题吧"是危险的想法
2. **隐瞒问题** —— 试图自己悄悄混过去，迟早会爆
3. **私自扩大范围** —— "顺便"改一下其他地方，大概率会出事
4. **硬扛不求助** —— 卡住了还死撑，浪费时间还可能搞坏东西
5. **一次性跑完** —— 十几二十个任务一口气做完，中间出了问题都不知道在哪
6. **机械执行不动脑** —— 计划是死的，人是活的，发现明显不对要提出来
7. **不看上下文** —— 执行任务前不看相关代码，上来就改

### ⚠️ 常见陷阱

1. **"就多做一点点"** —— 一点点累加起来就是大偏差。严格按计划来，想加的东西记下来，后面再说。
2. **"这个肯定没问题"** —— 越是这么想越容易出问题。验证一下花不了多少时间。
3. **"用户说随便搞"** —— 不，用户说随便搞不代表你可以乱来。该有的流程还是要有。
4. **"先做了再说"** —— 方向错了，做得越快偏得越远。每批的检查点就是为了及时纠偏。
5. **"验证太费时间"** —— 验证费时间，出了问题排查更费时间。自己选。

## 与其他技能的关系

| 技能 | 关系 | 说明 |
|------|------|------|
| **`writing-plans`** | 上游 | 先有计划，再执行。好的计划是顺利执行的前提 |
| **`brainstorming`** | 上游的上游 | 复杂需求先设计，再写计划，再执行 |
| **`requesting-code-review`** | 并行/下游 | 每批完成后可以做 code review，再继续 |
| **`git-commit`** | 并行 | 每个任务完成后可以单独提交，便于回溯 |
| **`feedback`** | 下游 | 执行中发现工具/平台问题，可以提交反馈 |

```
需求 → brainstorming → writing-plans → executing-plans → 完成
                          ↑                    │
                          │                    ↓
                          └──── 调整计划 ←── 遇到问题
```

## 红牌警告

以下情况出现时，**必须立即停止执行**并与用户沟通：

- ❌ 执行到第 2 个任务，发现第 1 个任务有问题 —— 停下来，先 fix
- ❌ 计划和实际代码差异很大 —— 不要硬套，先讨论调整
- ❌ 用户提了新需求/新想法 —— 记下来，不要偷偷加进去
- ❌ 连续两个任务验证失败 —— 大概率是方向错了，停下来复盘
- ❌ 用户说"等一下" —— 立刻停，不管做到哪
- ❌ 自己不确定对不对 —— 不确定就是有问题，先搞清楚
