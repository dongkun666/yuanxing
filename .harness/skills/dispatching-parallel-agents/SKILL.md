# 调度并行子代理 — Dispatching Parallel Agents

**核心理念（Superpowers）：** 一个大任务拆成 N 个小任务，同时派 N 个 agent 各自干，最后把结果拼起来。就像一个项目经理带着一队工程师同时开工——不是串行等一个做完再做下一个，而是多路并进。

**关键机制：**
- **单 message 多 task 调用**：一次发出多个 subagent 任务，并行执行
- **独立上下文**：每个 subagent 有自己的 context，互不干扰
- **物理隔离**：配合 `using-git-worktrees`，每个 subagent 在独立的 worktree 目录工作
- **结果聚合**：主 agent 负责收集、整合、验证所有子任务的产出

---

## 何时激活

### 必须激活（强场景）

- **Plan 多 track 并行执行** — 一个 Plan 里有 A1/A2/A3 多个 track，同时开工
- **跨服务功能开发** — 同时改 frontend + backend + ai-service + OCR，各干各的
- **多视角代码考古** — 同时从「前端调用链」「后端 API」「数据流向」多个角度排查问题
- **大规模重构** — 按模块拆分，多个 subagent 同时重构不同模块
- **多服务体检/巡检** — 同时检查多个服务的健康状态、依赖、配置
- **用户明确说"并行做"、"同时干"、"派几个 agent"**

### 建议激活（中场景）

- 单服务内多个独立模块的开发
- 同时写代码 + 写测试 + 写文档
- 大的 bug 修复需要同时从多个方向排查
- 需要对比多种实现方案，每个方案一个 subagent 做 PoC

### 不适用（弱场景）

- 任务本身就是串行的（第二步依赖第一步的结果）
- 单文件小改动，拆并行反而更慢
- 需求还不明确，需要先 brainstorm
- 改动范围极小，不值得调度 overhead

**判断口诀：** 能不能拆成「互不依赖、各自能验证」的几块？能 → 并行干；不能 → 老老实实串行。

└─────────────────────────────────────────────────────┘

### 第一步：任务分解（Task Decomposition）

**目标：** 把一个大任务拆成若干个「独立、可验证、无共享状态」的子任务。

#### 拆分原则

1. **独立可验证** — 每个子任务完成后，能独立验证它做对了没有，不需要等其他任务
2. **无共享状态** — 子任务之间不共享可变状态，不修改同一个文件的同一部分
3. **清晰接口** — 子任务之间的协作通过明确的接口（API 契约、数据格式、函数签名）进行
4. **粒度适中** — 每个子任务大约 30 分钟 ~ 2 小时工作量，太小了调度 overhead 大，太大了失去并行意义
5. **可衡量交付物** — 每个子任务有明确的「完成标准」和「产出物」

#### 拆分方法

**按技术层拆（最常用）：**
```
任务：实现用户登录功能
├── 前端子任务：登录页面 + 表单验证 + 调用 API
├── 后端子任务：登录 API + token 签发 + 密码校验
└── 测试子任务：e2e 测试 + 边界用例
```

**按模块拆：**
```
任务：重构合同审查模块
├── 子任务 A：解析器重构
├── 子任务 B：风险检测引擎重构
└── 子任务 C：报告生成器重构
```

**按关注点拆：**
```
任务：排查性能问题
├── 子任务 A：前端性能分析
├── 子任务 B：后端 API  profiling
└── 子任务 C：数据库查询优化
```

#### 拆分检查清单

- [ ] 每个子任务都能独立说清楚「做什么、怎么验收」吗？
- [ ] 两个子任务会不会改到同一个文件的同一处代码？
- [ ] 子任务之间的接口/契约明确吗？
- [ ] 有没有哪个子任务必须等另一个做完才能开始？
- [ ] 粒度合适吗？（不是 5 分钟的小事，也不是 2 天的巨无霸）

### 第二步：分配角色（Role Assignment）

**目标：** 给每个子任务分配合适的角色和技能配置，确保 subagent 有能力完成任务。

#### 标准角色配置

| 角色 | 适用场景 | 核心关注点 | 技能偏好 |
|---|---|---|---|
| **前端开发** | UI 实现、交互逻辑、前端样式、用户体验 | 视觉还原、交互流畅、响应式、可访问性 | 原生 JS、Tailwind CSS、HTML 结构 |
| **后端开发** | API 设计、业务逻辑、数据模型、服务集成 | 接口契约、数据一致性、性能、错误处理 | FastAPI、SQLite、Python 后端 |
| **AI 服务开发** | Prompt 工程、AI 能力集成、向量检索 | Prompt 质量、召回准确率、响应延迟 | LanceDB、OCR、LLM 集成 |
| **测试工程师** | 测试用例设计、自动化测试、质量保障 | 覆盖率、边界情况、回归测试 | pytest、e2e 测试、TDD |
| **代码审查员** | Code Review、质量把控、架构审视 | 代码质量、设计合理性、潜在风险 | 只读、批判性思维 |
| **文档工程师** | 技术文档、API 文档、使用说明 | 清晰度、准确性、完整性 | Markdown、示例代码 |

#### 角色分配注意事项

✅ **给每个 subagent 明确的「任务说明书」** — 做什么、不做什么、验收标准是什么
✅ **明确接口契约** — 前后端之间的 API 格式、数据结构要先定好
✅ **提供必要的上下文** — 相关文件路径、现有代码约定、项目规范
✅ **设定边界** — 告诉 subagent 哪些可以改、哪些不能改、有什么约束

❌ **不要给模糊的任务** — "把登录做一下" → 不行，要具体到页面、API、字段、验证规则
❌ **不要让两个 subagent 改同一个文件** — 除非你明确划分了区域，且它们不会冲突
❌ **不要假设 subagent 知道全局** — 每个 subagent 只有你给它的上下文

### 第三步：并行调度（Parallel Dispatch）

**目标：** 在**单条 message** 中同时调用多个 task tool，让所有 subagent 同时开工。

#### 调度方式

**核心机制：单 message 发多个 task tool 调用**

在你的回复中，同时发起多个 subagent 任务，它们会并行执行。这是真正的并行——不是串行等一个完了再开下一个。

#### 每个 Subagent 的任务模板

每个 subagent 任务都应该包含以下要素：

```
【角色】<角色名称，如：前端开发工程师>
【任务】<一句话描述任务目标>
【上下文】
- 相关文件：<列出关键文件路径>
- 接口契约：<如果有前后端交互，明确 API 格式>
- 项目规范：<引用 AGENTS.md 或相关规范>
【交付物】
- <明确的产出物 1>
- <明确的产出物 2>
【验收标准】
- <可验证的标准 1>
- <可验证的标准 2>
【约束】
- <不能做的事 1>
- <必须遵守的规则 1>
【Worktree】<对应的 worktree 路径>
```

#### 调度前检查清单

- [ ] 所有子任务都拆好了吗？每个都有明确的范围？
- [ ] 每个子任务都分配了合适的角色吗？
- [ ] 接口/契约都提前定义好了吗？
- [ ] 每个 subagent 都有独立的 worktree 吗？
- [ ] 有没有遗漏的依赖关系？（A 必须等 B 做完？）
- [ ] 主 agent 自己的工作是什么？（调度、集成、验证——不要也去写代码）

#### 主 Agent 的定位

**主 agent = 项目经理 + 集成工程师**

主 agent 的职责：
1. ✅ 拆解任务、定义接口
2. ✅ 分配角色、派发任务
3. ✅ 收集结果、整合代码
4. ✅ 集成验证、解决冲突
5. ✅ 最终交付、质量把关

主 agent **不应该**：
- ❌ 自己跳进去写业务代码（那是 subagent 的事）
- ❌ 频繁干预 subagent（给够上下文，信任它们）
- ❌ 在 main 分支上直接改（所有开发在 worktree 里）

### 第四步：结果聚合（Result Aggregation）

**目标：** 收集所有 subagent 的产出，整合到一起，验证整体是否工作。

#### 聚合流程

```
Subagent A 完成 → 产出 A
Subagent B 完成 → 产出 B    →    主 Agent 整合    →    集成验证    →    交付
Subagent C 完成 → 产出 C
```

#### 聚合步骤

**1. 逐个验收**

每个 subagent 完成后，先单独验收它的产出：
- 它的任务完成了吗？
- 交付物都在吗？
- 验收标准都满足吗？
- 代码质量过关吗？（必要时 dispatch code review）

**2. 代码合并**

将各 worktree 的改动合并回主分支：

```bash
# 回到主工作区
cd /path/to/main

# 逐个合并
git merge .worktrees/w10-a1-frontend
git merge .worktrees/w10-a2-backend
git merge .worktrees/w10-a3-tests
```

如果有冲突，解决冲突。

**3. 集成验证**

这是最关键的一步——单独都工作，合在一起不一定工作：

- 前后端 API 对得上吗？（请求格式、响应格式）
- 数据流能走通吗？（前端发请求 → 后端处理 → 数据库 → 返回结果）
- 所有功能一起跑，有没有互相影响？
- 有没有遗漏的集成点？

**4. 端到端测试**

如果有 e2e 测试，跑一遍。没有的话，手动走一遍核心流程。

**5. 最终交付**

- 确保 git status 干净
- 所有测试通过
- 文档更新了
- 给用户一个清晰的总结：做了什么、怎么验证的、有什么注意事项

#### 聚合时的常见问题

| 问题 | 原因 | 处理方式 |
|---|---|---|
| **merge 冲突** | 两个 subagent 改了同一个文件 | 分析冲突原因，合理合并，必要时找对应 subagent 确认 |
| **接口不匹配** | 前后端对 API 理解不一致 | 以预先定义的契约为准，哪边错了改哪边 |
| **功能有遗漏** | 任务拆分时有 gap | 补上，可能需要再 dispatch 一个小任务 |
| **集成后性能下降** | 各模块单独没问题，合起来慢 | profiling 定位瓶颈，针对性优化 |
| **测试覆盖不到位** | 各模块都有测试，但集成场景没测 | 补充集成测试 / e2e 测试 |

## 任务拆分原则详解

这是并行调度成败的关键——拆得好，一路顺畅；拆得不好，一地鸡毛。

### 原则 1：独立可验证

**每个子任务都应该能独立验证正确性。**

✅ 好的拆分：
- 前端：实现登录页面，能发请求（可以用 mock 后端验证）
- 后端：实现登录 API，能用 curl 调用验证
- 测试：编写测试用例，能独立运行

❌ 坏的拆分：
- 前端：实现登录页面的上半部分
- 后端：实现登录 API 的前半段
- （这俩单独都没法验证）

### 原则 2：无共享状态

**子任务之间不应该共享可变状态。**

✅ 好的拆分：
- 子任务 A：修改 `frontend/views/login.html`
- 子任务 B：修改 `backend/api/auth.py`
- （不同文件，互不干扰）

❌ 坏的拆分：
- 子任务 A：修改 `app.js` 里的登录逻辑
- 子任务 B：修改 `app.js` 里的注册逻辑
- （同一个文件，容易冲突，merge 头大）

**如果必须改同一个文件怎么办？**
- 方案一：串行做（不要强行并行）
- 方案二：明确划分区域，A 改上半部分，B 改下半部分（但仍有风险）
- 方案三：先把文件拆成多个模块，再并行（推荐）

### 原则 3：清晰接口

**子任务之间通过明确的接口协作，而不是共享内部实现。**

✅ 好的接口定义：
```
POST /api/auth/login
请求体：{ "username": "string", "password": "string" }
成功响应：{ "token": "string", "user": { "id": 1, "username": "..." } }
失败响应：{ "detail": "错误信息" }
状态码：200 成功 / 401 认证失败 / 422 参数错误
```

❌ 坏的接口定义：
```
"就做个登录接口，用户名密码登录，返回 token"
```
（太模糊，字段名呢？token 放哪？错误怎么返回？）

### 原则 4：先定契约，再开工

**接口契约必须在调度之前就定好，写在任务说明里。**

不要让前端和后端"各做各的，到时候再对"——大概率对不上。

正确流程：
1. 主 agent 先定义好 API 契约
2. 把契约写进两个 subagent 的任务说明里
3. 双方按契约开发
4. 集成的时候验证契约

## LexPrime 项目适配

### 强制约束：Worktree 物理隔离

**LexPrime 项目红线：绝对不要让两个并行 subagent 共享同一个 working tree。**

参考 `.harness/skills/using-git-worktrees/SKILL.md`。

#### 标准工作模式

```
main (主 agent 待在这里，只做调度和集成)
│
├── .worktrees/w10-a1-frontend/   ← subagent A (前端开发)
│   └── 分支: w10-a1-frontend
│
├── .worktrees/w10-a2-backend/    ← subagent B (后端开发)
│   └── 分支: w10-a2-backend
│
└── .worktrees/w10-a3-tests/      ← subagent C (测试工程师)
    └── 分支: w10-a3-tests
```

#### 调度前的准备步骤

```bash
# 1. 确保 main 是最新的
git checkout main
git pull origin main

# 2. 为每个子任务创建 worktree
git worktree add ".worktrees/w10-a1-frontend" -b "w10-a1-frontend"
git worktree add ".worktrees/w10-a2-backend" -b "w10-a2-backend"
git worktree add ".worktrees/w10-a3-tests" -b "w10-a3-tests"

# 3. 验证
git worktree list
```

### 典型场景：跨服务功能开发

以「合同审查功能」为例：

#### 第一步：主 agent 定义契约

**API 契约（预先定义好）：**
```
POST /api/contract-review/upload
请求: multipart/form-data { file: 合同文件 }
响应: { review_id: "string", status: "processing" }

GET /api/contract-review/{review_id}
响应: {
  status: "completed" | "processing" | "failed",
  result: {
    risks: [...],
    suggestions: [...],
    score: number
  }
}
```

#### 第二步：调度三个 subagent

**Subagent A — 前端开发**
- Worktree: `.worktrees/w10-a1-frontend`
- 任务：实现合同上传页面、进度展示、结果展示
- 交付物：HTML 页面、JS 逻辑、样式
- 验收：能上传文件、能轮询状态、能展示结果（可用 mock 数据验证）

**Subagent B — 后端开发**
- Worktree: `.worktrees/w10-a2-backend`
- 任务：实现上传 API、状态查询 API、调用 AI 服务
- 交付物：FastAPI 路由、业务逻辑、数据模型
- 验收：curl 能调用、状态流转正确、数据库存储正常

**Subagent C — AI 服务开发**
- Worktree: `.worktrees/w10-a3-ai`
- 任务：实现合同审查 prompt、风险检测逻辑、结果格式化
- 交付物：Prompt 模板、解析逻辑、风险规则
- 验收：给定合同文本，能输出结构化的审查结果

#### 第三步：结果聚合 & 集成验证

三个 subagent 都完成后：
1. 逐个验收各自的产出
2. 合并三个分支到 main
3. 启动所有服务，端到端走一遍流程
4. 验证：上传合同 → 后台处理 → AI 分析 → 前端展示结果
5. 有问题就修，没问题就交付

### 典型场景：多服务体检

每周一次的全服务健康检查：

**Subagent A — Frontend 巡检**
- 检查：代码质量、未使用的变量、性能瓶颈、可访问性问题
- 工具：eslint、lighthouse（如果有）、手动代码审查

**Subagent B — Backend 巡检**
- 检查：API 响应时间、错误率、数据库查询、依赖安全
- 工具：pytest、bandit、sql 慢查询分析

**Subagent C — AI Service 巡检**
- 检查：Prompt 质量、召回准确率、OCR 成功率、响应延迟
- 工具：测试集跑一遍、对比 baseline

每个 subagent 输出一份体检报告，主 agent 汇总成总报告。

## 注意事项与陷阱

### ❌ 常见错误

#### 1. 任务拆得不好，依赖关系没理清

**表现：** A 做到一半发现需要 B 的结果，卡住了。

**原因：** 拆分时没考虑清楚依赖关系，强行并行。

**解决：**
- 拆分时画个依赖图，哪些可以并行，哪些必须串行
- 真有依赖的，就按顺序来，不要强行并行
- 或者把 A 拆成「不依赖 B 的部分」和「依赖 B 的部分」，前半部分并行，后半部分串行

#### 2. 接口契约没定好，集成时发现对不上

**表现：** 前端发的请求格式后端不认，后端返回的字段前端不用。

**原因：** 调度前没定义清晰的接口契约，双方各想各的。

**解决：**
- 调度前，主 agent 必须把接口契约写清楚
- 字段名、数据类型、错误格式、状态码——都要明确
- 把契约复制到每个相关 subagent 的任务说明里

#### 3. 两个 subagent 改了同一个文件

**表现：** merge 冲突一大堆，不知道谁的是对的。

**原因：** 任务拆分时没注意，让两个 subagent 改到一块儿去了。

**解决：**
- 拆分时检查：会不会改到同一个文件？
- 真需要改同一个文件，就串行做，或者拆文件
- 不要侥幸心理——"应该不会冲突吧" → 大概率会

#### 4. 主 agent 自己也去写代码了

**表现：** 主 agent 一边调度，一边自己也改代码，结果自己的改动和 subagent 的冲突了。

**原因：** 没搞清楚主 agent 的定位。

**解决：**
- 主 agent = 项目经理 + 集成工程师
- 所有开发工作都交给 subagent
- 主 agent 待在 main 分支，不动业务代码
- 真要改，也等集成的时候再改

#### 5. 忘了 worktree 隔离

**表现：** 两个 subagent 都在 main 上改，互相覆盖，phantom diff。

**原因：** 偷懒，没建 worktree。

**解决：**
- LexPrime 项目强制要求：并行 subagent 必须用 worktree
- 不要心存侥幸，"就改一点点" → 也不行
- 参考 `using-git-worktrees` skill

#### 6. 验收标准模糊，不知道算不算做完了

**表现：** subagent 说"做完了"，主 agent 一看，离预期差远了。

**原因：** 任务说明里的验收标准太模糊。

**解决：**
- 每个子任务都要有明确、可验证的验收标准
- 用"能做 X"、"返回 Y"、"通过 Z 测试"这种具体的描述
- 不要用"做好"、"完善"、"优化"这种模糊的词

### ✅ 最佳实践

#### 1. 先小范围试验，再大规模并行

如果你第一次用并行调度，先从 2 个 subagent 开始试试手，熟练了再加到 3 个、4 个。

#### 2. 接口契约越详细越好

花 10 分钟把契约写清楚，能省下集成时 1 小时的扯皮和修改。

#### 3. 每个 subagent 的任务说明要完整

不要假设 subagent 知道上下文。把它需要知道的都写进去：
- 做什么
- 相关文件在哪
- 有什么规范要遵守
- 交付物是什么
- 怎么验收
- 什么不能做

#### 4. 主 agent 保持全局视野

主 agent 不要陷入细节，要关注：
- 整体进度
- 子任务之间的衔接
- 集成风险
- 最终交付质量

#### 5. 集成验证一定要做

每个子任务单独都通过了，不代表合在一起能工作。集成验证是必须的。

#### 6. 及时清理 worktree

任务完成后，删掉不用的 worktree，保持工作区整洁。

| **git-commit** | 配合 | 每个 subagent 在自己的 worktree 里独立 commit |

## 红牌警告

出现以下情况，说明你的并行调度可能出问题了：

- ❌ 你在 main 分支上直接改代码，同时还有 subagent 在跑
- ❌ 两个 subagent 的任务说明里提到了同一个文件
- ❌ 接口契约只有一句话，没有具体字段和格式
- ❌ 你自己也在写业务代码，同时还在调度 subagent
- ❌ subagent 问你"这个怎么做"，你才发现之前没说清楚
- ❌ 集成的时候发现前后端完全对不上
- ❌ merge 冲突了十几个文件
- ❌ 你说不清每个 subagent 具体在做什么、做到哪了

如果出现以上情况，停下来，重新梳理任务拆分和接口契约，不要硬着头皮继续。

## 总结

调度并行子代理的核心精髓：

1. **拆得开** — 任务能拆成独立、可验证、无共享状态的子任务
2. **定得清** — 接口契约提前定义清楚，双方按契约开发
3. **隔得离** — 每个 subagent 在独立 worktree 工作，物理隔离
4. **合得拢** — 最后能顺利集成到一起，整体验证通过

掌握了这项技能，你就能从「一个人干活」变成「带着一队人干活」，效率翻倍。

🚀 **并行起来，让多个 agent 同时为你工作！**
