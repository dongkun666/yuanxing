# Writing Plans — 编写开发计划

将复杂的开发工作分解为一系列小而独立的任务，每个任务都有明确的目标、精确的文件路径、完整的代码实现和可执行的验证步骤。

**核心原则：先计划，后执行。计划越详细，执行越顺利。**

## 何时激活

**必须激活（强制）：**

- 开始任何涉及 2 个或更多文件的开发任务
- 实现新功能或新模块
- 重构现有代码（无论范围大小）
- 修复复杂 bug（跨文件、跨模块、或需要深入分析）
- 任何你不确定最终需要多少步骤的任务

**可选激活：**

- 单文件但逻辑复杂的修改
- 需要多个步骤的配置变更
- 你想留下可追溯文档的任务

**跳过：**

- 纯文档修改（typo、注释更新）
- 单行代码修复且影响范围明确
- 完全机械的重命名操作（且已确认无副作用）

## 工作流程

### 第一步：理解需求

在写计划之前，确保你完全理解：

1. **目标是什么？** — 最终要达成什么效果
2. **约束条件是什么？** — 技术栈、性能要求、兼容性等
3. **现有代码结构如何？** — 先探索相关文件，不要在真空中写计划

> 💡 **提示：** 如果需求不明确，先提问澄清，不要猜测。

### 第二步：分解任务

将整体工作分解为多个小任务，遵循以下规则：

#### 任务粒度

- **每个任务预计耗时 2-5 分钟** — 既能保持节奏，又足够小到可以一次性完成
- **每个任务只做一件事** — 单一职责原则
- **任务之间尽量独立** — 理想情况下可以按顺序执行，前一个失败不影响后一个的理解

#### 分解策略

1. **自顶向下** — 先列大的阶段，再拆分成小任务
2. **按文件边界拆分** — 每个任务尽量只修改一个文件（除非文件间强耦合）
3. **先基础设施，后业务逻辑** — 类型定义 → 工具函数 → 核心逻辑 → 集成
4. **先易后难** — 把简单的任务放在前面，建立信心和势头

### 第三步：为每个任务编写详细说明

每个任务必须包含以下要素：

#### 1. 任务编号和标题

清晰简洁地描述这个任务要做什么。

#### 2. 精确的文件路径

- 列出任务会**创建**或**修改**的所有文件
- 使用绝对路径或相对于项目根目录的路径
- 不要写"某个文件"或"相关文件"——必须精确

#### 3. 完整的代码实现

- 如果是创建新文件：写出完整的文件内容
- 如果是修改现有文件：写出精确的修改位置（行号或上下文）和新代码
- 代码应该是**可以直接复制粘贴**的程度，不需要执行者再思考

> ⚠️ **重要：** 计划阶段的代码不需要 100% 完美，但必须足够详细，让执行者知道要做什么。执行时可以根据实际情况微调，但大方向不能错。

#### 4. 验证步骤

每个任务完成后如何验证它是正确的？

- 运行特定的测试命令
- 检查特定的输出
- 执行特定的操作并观察结果
- 编译/类型检查通过

验证步骤必须是**可执行、可验证**的，不能是"检查是否正常工作"这种模糊的描述。

### 第四步：应用 YAGNI 原则

**YAGNI = You Aren't Gonna Need It（你不会需要它）**

在写计划时，不断问自己：

- ❌ "这个功能将来可能会用到" — 不要加
- ❌ "这样设计更灵活" — 除非当前需求确实需要
- ✅ "这是完成当前任务所必需的" — 保留
- ✅ "不这样做就无法工作" — 保留

> 💡 **经验法则：** 如果你无法指出现有需求中哪一条需要这个设计，那就删掉它。

### 第五步：应用 DRY 原则

**DRY = Don't Repeat Yourself（不要重复自己）**

检查计划中的所有任务：

- 是否有重复的代码模式？如果有，考虑提取为公共函数/组件
- 是否有重复的逻辑？如果有，考虑统一处理
- 但是！不要为了 DRY 而 DRY —— 如果抽象会增加复杂度，且重复只有 2 处，宁可重复

> ⚠️ **注意：** YAGNI 优先于 DRY。不要为了消除重复而引入你不需要的抽象。

### 第六步：审查和调整

完成初稿后，回过头来整体审视：

1. **顺序是否合理？** — 依赖关系是否正确
2. **是否有遗漏？** — 有没有什么工作没被覆盖
3. **是否有多余？** — 有没有什么任务是不需要的
4. **粒度是否合适？** — 有没有太大或太小的任务
5. **验证是否充分？** — 每个任务的验证步骤是否真的能验证正确性

## 计划格式

### 标准计划模板

```markdown
# 计划：[功能/修复名称]

## 概述
- **目标：** [一句话描述目标]
- **背景：** [为什么要做这件事，相关上下文]
- **预期成果：** [完成后会是什么样子]

## 任务列表

### 任务 1：[任务标题]
- **文件：**
  - `path/to/file1.ts` (创建)
  - `path/to/file2.ts` (修改)
- **实现：**
  ```typescript
  // 完整的代码
  ```
- **验证：**
  1. 运行 `npm run test -- file1.test.ts`
  2. 检查类型：`npx tsc --noEmit`

### 任务 2：[任务标题]
...

## 风险和注意事项
- [可能遇到的问题或需要特别注意的地方]

## 完成标准
- [ ] 所有任务完成
- [ ] 所有测试通过
- [ ] [其他验收标准]
```

### YAML 格式（可选，用于机器读取）

如果需要机器处理计划，可以使用 YAML 格式：

```yaml
plan:
  id: plan-001
  name: "实现用户认证模块"
  version: "1.0"
  status: "pending"
  
  tasks:
    - id: task-1
      title: "定义用户类型接口"
      files:
        - path: "src/types/user.ts"
          action: "create"
      code: |
        export interface User {
          id: string;
          name: string;
          email: string;
        }
      verification:
        - command: "npx tsc --noEmit src/types/user.ts"
          expected: "无错误输出"
    
    - id: task-2
      title: "实现用户认证服务"
      files:
        - path: "src/services/auth.ts"
          action: "create"
      depends_on: ["task-1"]
      # ...
```

## 任务粒度指南

| 粒度 | 耗时 | 适用场景 | 示例 |
|------|------|----------|------|
| 过小 | < 1 分钟 | 一般避免，除非是收尾工作 | 修改一个变量名 |
| 合适 | 2-5 分钟 | 标准任务大小 | 实现一个工具函数 + 测试 |
| 偏大 | 5-10 分钟 | 可以接受，但考虑拆分 | 实现一个完整的组件 |
| 过大 | > 10 分钟 | 必须拆分 | 实现整个模块 |

### 如何判断任务是否太大？

如果你对一个任务说：
- "这个任务包含好几个部分" → 拆
- "先做 A，再做 B" → 拆成两个
- "这里有好几步" → 每步一个任务

## 注意事项

### ✅ 应该做的

1. **先探索代码库** — 在写计划之前，充分了解现有结构
2. **写清楚每个文件的路径** — 精确到文件名，不要模糊
3. **提供完整的代码** — 让执行者可以直接使用
4. **每个任务都有验证步骤** — 确保可验证
5. **保持任务顺序合理** — 先依赖，后使用
6. **定期回顾计划** — 执行中发现问题及时调整
7. **记录决策过程** — 为什么这样设计，方便以后回顾

### ❌ 不应该做的

1. **在真空中写计划** — 不看现有代码就开始设计
2. **任务描述模糊** — "实现相关功能"这种话毫无意义
3. **跳过验证步骤** — 无法验证的任务等于没做
4. **过度设计** — YAGNI！只做当前需要的
5. **任务太大** — 一个任务做十几件事
6. **计划赶不上变化就放弃计划** — 计划可以调整，不是一成不变的
7. **为了符合计划而硬凑** — 如果实际情况和计划不符，修改计划，而不是硬来

## 计划与实际执行的关系

计划是**指导**，不是**枷锁**。

- **执行前：** 认真写计划，想清楚再做
- **执行中：** 发现问题及时调整计划，记录变更原因
- **执行后：** 回顾计划，看看哪些估对了，哪些估错了，下次改进

> 💡 **名言：** 计划毫无价值，但规划过程不可或缺。—— 德怀特·艾森豪威尔

## 与其他技能的配合

- **`requesting-code-review`** — 每个任务完成后，可以请求代码审查
- **`git-commit`** — 每个任务完成后，进行一次逻辑提交
- **`web-dev`** — 如果是 Web 开发任务，在计划阶段考虑 UI/UX

## 红牌警告

- ❌ 一上来就写代码，完全不做计划
- ❌ 计划只有标题，没有具体内容
- ❌ 一个任务包含 10 个文件修改
- ❌ 验证步骤是"看看对不对"
- ❌ 为了"将来可能有用"加一堆功能
- ❌ 发现计划错了还硬着头皮执行
- ❌ 计划写完就扔到一边，执行时完全不看
