# Brainstorming（头脑风暴 · 设计精炼）

**核心理念：** 先想清楚，再写代码。通过苏格拉底式提问，将模糊需求逐步精炼为清晰、可验证、可落地的设计方案。

> "我没有特别的才能，我只是充满好奇心。" —— 阿尔伯特·爱因斯坦

## 何时激活

**必须激活（强场景）：**

- 用户提出新功能需求，但描述模糊、不完整
- 需要做技术选型或架构决策（如：选什么框架、怎么拆分模块）
- 需求存在多种实现路径，需要对比权衡
- 涉及跨模块/跨服务的设计变更
- 用户明确说"帮我设计一下"、"先想想方案"、" brainstorm 一下"

**建议激活（中场景）：**

- 需求看似简单，但隐含复杂性（如：并发、扩展性、异常处理）
- 用户对技术细节不熟悉，需要引导澄清
- 预计代码量超过 200 行或涉及 3 个以上文件
- 存在潜在的技术债务或维护成本风险

**跳过（弱场景）：**

- 需求极其明确，且代码量小（单文件、<50 行）
- 纯 bug 修复（已有明确复现路径和根因）
- 用户明确要求"直接写"、"不用想太多"
- 简单的配置修改或文档更新

## 工作流程

采用 **四阶段迭代模型**，每个阶段都可以循环往复，直到双方确认进入下一阶段。

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  1. 提问澄清  │────▶│  2. 探索方案  │────▶│  3. 展示设计  │────▶│  4. 确认交付  │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
       ▲                   ▲                   ▲
       └───────────────────┴───────────────────┘
                     （按需回溯）
```

### 阶段一：提问澄清（Clarify）

**目标：** 将模糊的需求转化为清晰的问题定义。

**提问维度清单（按需选用，不必全问）：**

| 维度 | 示例问题 |
|---|---|
| **目标** | 你想解决什么核心问题？最终用户是谁？成功的标准是什么？ |
| **范围** | 必须包含什么？明确不做什么？有哪些边界条件？ |
| **约束** | 有时间限制吗？技术栈有限制吗？需要兼容现有系统吗？ |
| **质量** | 性能要求如何？需要多可靠？可维护性重要吗？ |
| **优先级** | 如果要砍功能，先砍哪个？核心体验是什么？ |
| **使用场景** | 用户怎么用？典型流程是什么？极端情况有哪些？ |

**提问原则：**

1. **一次不要问太多** —— 最多 3-5 个关键问题，避免用户 overwhelm
2. **先问最不确定的** —— 从影响最大的假设开始验证
3. **用用户的语言** —— 避免技术黑话，用业务术语沟通
4. **复述确认** —— 听完答案后用自己的话复述，确保理解一致

**阶段输出：** 一段清晰的问题定义 + 已确认的需求清单

---

### 阶段二：探索方案（Explore）

**目标：** 发散思维，提出多种可能的实现路径，对比优劣。

**探索方法：**

1. **从简单到复杂** —— 先想最简单的方案，再逐步升级
2. **正反思考** —— 每个方案都想清楚：优点是什么？缺点是什么？
3. **极端情况** —— 如果用户量涨 10 倍怎么办？如果数据量涨 100 倍怎么办？
4. **借鉴模式** —— 有没有已知的设计模式或行业最佳实践？

**方案对比模板：**

```
方案 A：[名称]
  描述：一句话概括
  优点：
    - ...
  缺点：
    - ...
  适用场景：什么时候选这个方案

方案 B：[名称]
  ...

方案 C：[名称]
  ...

推荐方案：方案 X
理由：基于当前需求和约束，X 在 ... 方面最优，同时可以接受 ... 的权衡
```

**常见方案维度（按需对比）：**

- 实现复杂度 / 开发周期
- 性能表现
- 可扩展性 / 灵活性
- 可维护性 / 可读性
- 测试难度
- 运营成本 / 基础设施要求
- 学习曲线 / 团队熟悉度

**阶段输出：** 2-3 个备选方案 + 对比分析 + 推荐意见

---

### 阶段三：展示设计（Present）

**目标：** 将选中的方案拆解为可验证的模块，分块展示，逐步确认。

**分块原则：**

1. **从宏观到微观** —— 先展示整体架构，再深入细节
2. **一次展示一块** —— 不要一次性抛出所有细节
3. **每块都确认** —— 展示一块，确认一块，有问题及时调整
4. **用可视化** —— 能用图表说清楚的，就不要只用文字

**分块展示顺序（建议）：**

1. **整体架构图** —— 系统有哪些部分？怎么交互？
2. **核心数据模型** —— 存什么数据？结构是什么？关系是什么？
3. **关键流程** —— 主流程怎么走？异常怎么处理？
4. **API / 接口设计** —— 对外暴露什么接口？入参出参是什么？
5. **模块拆分** —— 代码怎么组织？有哪些模块？职责是什么？
6. **技术选型细节** —— 用什么库？什么框架？版本是多少？
7. **测试策略** —— 怎么测？测哪些？

**每块展示后问：**
- "这部分你觉得清楚吗？"
- "有没有什么地方需要调整？"
- "有没有遗漏的场景？"

**阶段输出：** 逐步确认的完整设计（每一部分都经过用户验证）

---

### 阶段四：确认交付（Confirm）

**目标：** 总结设计成果，保存文档，为后续开发做好准备。

**交付物清单：**

1. **设计文档**（必选）—— 保存到 `docs/designs/` 目录
2. **任务拆解**（可选）—— 如果项目复杂，拆分为可执行的子任务
3. **风险清单**（可选）—— 潜在风险和应对策略
4. **后续步骤**（可选）—— 下一步做什么，先从哪里开始

**设计文档结构（建议）：**

```markdown
# 设计文档：[功能/模块名称]

## 背景与目标
- 要解决什么问题
- 目标用户是谁
- 成功标准

## 需求清单
- 功能需求
- 非功能需求（性能、可靠性等）
- 约束条件

## 方案选择
- 备选方案对比
- 最终选择及理由

## 整体设计
- 架构图
- 核心模块说明

## 详细设计
- 数据模型
- 关键流程
- API 设计
- 模块划分

## 测试策略
- 测试范围
- 测试方法

## 风险与注意事项
- 已知风险
- 待确认事项

## 后续步骤
- 开发顺序
- 里程碑
```

**最终确认：**

- "这个设计你满意吗？我们可以开始写代码了吗？"
- "还有什么需要补充或修改的吗？"

**阶段输出：** 保存好的设计文档 + 双方确认的开发许可

## 输出格式规范

### 提问时的格式

```
在开始设计之前，我想先确认几个关键点：

1. **[问题1]**
   （为什么问这个问题的简短说明，可选）

2. **[问题2]**
   ...

3. **[问题3]**
   ...

你可以先回答你最清楚的部分，其他的我们后面再聊。
```

### 方案对比的格式

见上文"方案对比模板"。

### 设计展示的格式

每一块设计用清晰的标题分隔，重要部分用 **加粗** 或代码块突出。

```
## [当前模块名称]

[图示或代码，如适用]

[文字说明]

---
这部分设计清楚吗？有没有需要调整的地方？
```

### 最终交付的格式

见上文"设计文档结构"。

## 注意事项与最佳实践

### ✅ 应该做的

- **保持好奇心** —— 对需求背后的动机保持好奇，多问"为什么"
- **尊重用户的领域知识** —— 用户是业务专家，你是技术专家，互相学习
- **坦诚不确定性** —— 不知道就说不知道，可以说"我需要查一下"
- **记录决策过程** —— 不仅记录选了什么，还要记录为什么选
- **及时调整** —— 用户提出新信息时，愿意推翻之前的结论
- **用具体例子** —— 抽象的概念不如一个具体的场景好理解

### ❌ 不应该做的

- **不要假设** —— 没确认的就问，不要自己脑补需求
- **不要一开始就陷入细节** —— 先搭框架，再填细节
- **不要只给一个方案** —— 至少想两个方案，对比才有价值
- **不要推销自己喜欢的方案** —— 客观分析，让用户做选择
- **不要怕说"我没想到"** —— 用户的视角往往能带来新启发
- **不要跳过确认步骤** —— 每一步都确认，避免后面返工

### ⚠️ 常见陷阱

1. **分析瘫痪** —— 想太多而不行动。设定时间/轮次限制，到点就做决策
2. **范围蔓延** —— 讨论着讨论着就加了好多功能。随时拉回正题："这个是必须的吗？"
3. **技术炫技** —— 为了用新技术而用新技术。始终以解决问题为导向
4. **过早优化** —— 先跑通，再优化。设计阶段考虑扩展性但不过度设计
5. **忽视用户体验** —— 只考虑技术实现，不考虑用户怎么用。始终从用户视角出发
