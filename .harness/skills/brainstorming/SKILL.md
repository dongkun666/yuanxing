# Brainstorming — 设计构思与需求拆解

## 触发条件

**必须激活：**
- 用户提出新功能、新页面、新模块需求
- 涉及 3+ 文件的改动
- 前后端联动的功能（前端 view + FastAPI endpoint + 数据模型）
- 对现有架构有影响的改动

**可跳过：**
- 单文件 typo / 文案修改
- 已有明确设计文档的微调
- 紧急 hotfix（事后补设计文档）

## 核心原则

> **HARD-GATE：设计未获用户确认前，绝不写一行代码。**

- 一次只问一个问题，不轰炸用户
- 优先给选择题（2-3 个选项 + 推荐）
- YAGNI：砍掉所有"可能会用到"的功能
- 律师单人版边界：不加律所管理、公开数据、协作功能

## 步骤流程

### 第 1 步：探索项目上下文（5 分钟）
- 读 `AGENTS.md`、`DESIGN.md`、相关 PRD
- 看 `templates/views/` 现有页面模式
- 看 `backend/cases-crawler/` 后端结构
- 查最近相关提交

### 第 2 步：澄清需求（一问一答）
聚焦三个维度，每次只问一个：
1. **目的**：这个功能解决什么具体问题？给谁用？
2. **约束**：有什么技术/产品/合规限制？
3. **成功标准**：怎么算做好了？用户怎么验证？

> 前端必问：新 view 还是改现有 view？和哪个现有页面最像？
> 后端必问：新 endpoint 还是扩展现有的？数据存哪里？SQLite / LanceDB / 内存？

### 第 3 步：提出 2-3 个方案
每个方案包含：
- 方案名 + 一句话简介
- 优点 / 缺点
- 改动范围（前端 / 后端 / 数据模型）
- 你的推荐 + 理由

**方案粒度模板（LexPrime 适配）：**
- **方案 A 极简**：只做核心路径，UI 复用现有组件
- **方案 B 标准**：完整功能 + 错误处理 + 基础测试
- **方案 C 完整**：含边缘情况 + 优化 + 完整测试覆盖

### 第 4 步：分段呈现设计，逐段确认
按以下分段，每段呈现后等用户确认再继续：

1. **架构概览**（数据流向图 + 模块边界）
2. **前端设计**：view 名称、HTML 结构、JS 模块划分、Tailwind 样式策略
3. **后端设计**：FastAPI endpoint（路径/方法/请求/响应）、数据模型、服务层
4. **数据设计**：表结构 / 向量库 schema / 数据迁移策略
5. **错误处理**：前端提示、后端错误码、日志策略
6. **测试策略**：单元测试 / e2e 测试范围

### 第 5 步：写设计文档 + 自检
保存到：`docs/plans/YYYY-MM-DD-<topic>-design.md`

**自检清单（必须全部通过）：**
- [ ] 没有 TBD / TODO / 待补充
- [ ] 前后端接口契约明确（请求/响应字段、类型、状态码）
- [ ] 没有"适当的错误处理"这类空话
- [ ] 和现有 AGENTS.md 中的硬规则不冲突
- [ ] 没有恢复已删除的模块（cases-db / laws-db 等）

### 第 6 步：用户审核文档 → 进入 writing-plans
用户确认设计文档后，调用 `writing-plans` 技能进入实施计划阶段。

## 检查清单

| 检查项 | 状态 |
|--------|------|
| 项目上下文已探索 | ☐ |
| 需求三要素（目的/约束/成功标准）已澄清 | ☐ |
| 2-3 个方案已提出，推荐方案明确 | ☐ |
| 设计分段呈现，逐段获确认 | ☐ |
| 设计文档已写入 docs/plans/ | ☐ |
| 自检 6 项全部通过 | ☐ |
| 用户已书面确认设计 | ☐ |

## 常见陷阱

- ❌ "这个简单，直接做吧" → 简单功能最容易踩假设的坑
- ❌ 一次抛 5 个问题 → 用户会跳过思考
- ❌ 设计里塞"以后会用"的功能 → YAGNI
- ❌ 模糊的接口定义 → 前后端联调必出问题
- ❌ 违反律师单人版边界 → 加律所/协作功能
