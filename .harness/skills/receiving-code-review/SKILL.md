# Receiving Code Review — 接收代码审查

**核心理念：验证优先于同意。不要表演式接受，要有技术依据地反驳。**

代码审查不是"上级审批"，而是两个工程师之间的技术对话。审查者可能犯错，你也可能犯错——关键是用代码、测试和事实说话，而不是用态度或立场。

> "代码审查的目的不是证明你是对的，而是找到正确答案。" —— 某位睿智的工程师

---

## 何时激活

**必须激活（强场景）：**

- 收到任何代码审查反馈（无论是来自人类还是 AI 审查者）
- `requesting-code-review` 技能返回审查结果后
- 有人对你的代码提出修改建议或指出问题
- 你需要决定是否采纳、反驳或记录某条审查意见

**建议激活（中场景）：**

- 收到模糊的反馈，需要澄清
- 对某条意见有不同看法，需要组织反驳思路
- 需要将审查意见整理为可执行的任务列表

**跳过（弱场景）：**

- 纯赞美、无具体意见的反馈
- 你已经完全同意且计划立即修改的简单意见
- 明确的 typo 修复建议（直接改就是了）

---

## 响应流程

采用 **验证 → 复述 → 决策** 三段式流程，确保每一步都基于事实，而不是情绪或直觉。

```
┌─────────────┐     ┌─────────────┐     ┌──────────────────────┐
│  1. 验证     │────▶│  2. 复述     │────▶│  3. 决策（接受/反驳） │
└─────────────┘     └─────────────┘     └──────────────────────┘
       │                   │                        │
       ▼                   ▼                        ▼
  用代码/测试/复现     用自己的话重述          接受 → 修复
  验证问题是否存在     确保理解一致            反驳 → 举证
                                                记录 → TODO
```

### 第一步：验证（Verify）

**目标：在回应之前，先确认审查意见是否成立。**

**验证清单：**

| 验证项 | 怎么做 |
|---|---|
| **问题是否真的存在？** | 去看对应的代码，复现问题，运行测试 |
| **理解是否一致？** | 审查者说的"问题"和你理解的是一回事吗？ |
| **影响有多大？** | 真的会导致 bug 吗？还是只是风格偏好？ |
| **有没有反例？** | 现有的代码/测试是否已经覆盖了这个场景？ |

**验证原则：**

1. **先看代码再回应** —— 不要凭记忆反驳，打开文件确认
2. **能跑就跑** —— 可以运行的就运行，用输出说话
3. **区分事实和观点** —— "这段代码会导致空指针"是可验证的事实；"这段代码写得不好"是观点
4. **不确定就说不确定** —— "我需要验证一下"比硬撑着反驳强

> ⚠️ **关键：** 永远不要在未验证的情况下直接说"你错了"。先验证，再下结论。

---

### 第二步：复述（Restate）

**目标：用自己的话重述审查意见，确保双方理解一致。**

**为什么要复述？**

- 很多分歧源于理解不一致，而不是技术判断不同
- 复述让审查者知道你在认真听，而不是急着反驳
- 复述可以暴露理解偏差，避免鸡同鸭讲

**复述模板：**

```
我理解你的意思是：
  [用自己的话重述问题]
  具体来说，在 [文件:行号] 这里，[描述问题场景]
  可能导致 [后果]

我理解的对吗？
```

**复述技巧：**

- 用你自己的话，不要原样复制
- 具体化：说出文件、行号、场景
- 说出后果：这个问题会导致什么
- 最后确认理解是否一致

---

### 第三步：决策（Decide）

根据验证结果，选择以下三种行动之一：

#### 选项 A：接受并修复

**条件：验证确认问题存在，且审查意见正确。**

**行动：**
1. 承认问题："你说得对，这里确实有问题"
2. 说明修复方案
3. 立即修复（根据严重级别，见下文）

#### 选项 B：有理有据地反驳

**条件：验证后确认审查意见不正确、不完整或有偏差。**

**行动：**
- 用代码、测试、复现结果作为证据
- 清晰说明为什么审查意见不成立
- 保持技术讨论的态度，对事不对人

详见下文"如何有效反驳"。

#### 选项 C：记录为 TODO（部分接受）

**条件：问题存在，但当前不值得阻塞进度。**

**行动：**
- 承认问题存在
- 说明为什么现在不修复（优先级、范围、风险等）
- 记录为 TODO，承诺后续处理
- 通常用于 Minor 级别的问题

---

## 严重级别处理

审查意见按严重程度分为三级，对应不同的响应策略。

### 🔴 Critical（严重）— 立即修复，阻塞提交

**定义：** 会导致生产事故、数据丢失、安全漏洞、系统崩溃的问题。

**示例：**
- 空指针/越界访问会导致 crash
- 并发安全问题（竞态条件、死锁）
- 安全漏洞（SQL 注入、XSS、认证绕过）
- 数据不一致或数据丢失
- 破坏已有功能的回归 bug

**处理规则：**
- ✅ 必须立即修复，不修复不能继续
- ✅ 修复后重新请求审查
- ❌ 不能"以后再修"
- ❌ 不能用 TODO 糊弄过去

**响应模板：**
```
你说得对，这确实是个严重问题。我来修复它。

修复方案：[简要说明怎么修]
修复后我会重新请你审查。
```

---

### 🟡 Important（重要）— 修完再继续下一任务

**定义：** 不会立即导致事故，但会埋下隐患、增加维护成本或违反设计原则的问题。

**示例：**
- 代码逻辑错误但当前不会触发（边缘 case）
- 缺少错误处理或错误处理不当
- 重复代码、职责不清
- 违反项目约定或架构原则
- 性能问题（非关键路径，但有明显优化空间）

**处理规则：**
- ✅ 在进入下一个任务之前修复
- ✅ 可以批量修复多个 Important 问题
- ❌ 不能带着 Important 问题进入新任务
- ❌ 不能无限期推迟

**响应模板：**
```
同意，这个问题需要修复。我会在完成当前任务后、开始下一个任务之前处理。

修复思路：[简要说明]
```

---

### 🟢 Minor（轻微）— 记 TODO，不阻塞

**定义：** 代码风格、命名、注释、可读性优化等，不影响功能正确性的问题。

**示例：**
- 命名可以更清晰
- 可以加个注释
- 代码风格不一致（但项目没有强制规范）
- 可以简化的写法（但当前写法也正确）
- "如果是我会这样写"类的个人偏好

**处理规则：**
- ✅ 可以记录为 TODO，不阻塞提交
- ✅ 如果顺手就改了，不强求
- ✅ 如果不同意，可以礼貌说明理由
- ❌ 不要因为 Minor 问题阻塞进度
- ❌ 不要为了 Minor 问题争论不休

**响应模板：**
```
有道理，我记下来了。这个不阻塞当前进度，我后面统一优化。

TODO: [记录问题]
```

## 如何有效反驳

**核心原则：反驳的是观点，不是人。用证据说话，而不是用态度说话。**

### 什么时候该反驳

- 审查意见基于错误的事实或误解
- 审查者忽略了重要的上下文或约束
- 建议的方案有隐藏的问题或代价
- 问题确实存在，但修复的代价远大于收益
- 审查意见是纯主观偏好，没有客观依据

### 什么时候不该反驳

- 问题确实存在，只是你不想改
- 纯风格问题且项目有明确规范（按规范来）
- 你只是想赢，而不是找到正确答案
- 你的反驳没有证据，只是"我觉得"

---

### 有效反驳的四步法

```
┌─────────────┐
│  1. 肯定部分  │  —— 先同意你同意的部分，建立共识
└─────────────┘
       │
       ▼
┌─────────────┐
│  2. 提出不同  │  —— 清晰说出你的不同意见
└─────────────┘
       │
       ▼
┌─────────────┐
│  3. 出示证据  │  —— 代码、测试、复现、文档、性能数据
└─────────────┘
       │
       ▼
┌─────────────┐
│  4. 保持开放  │  —— 邀请对方回应，愿意被说服
└─────────────┘
```

#### 第一步：肯定部分

先找你同意的地方，建立共识基础。

**示例：**
- "你说的对，这里确实需要处理边界情况"
- "我同意可读性很重要"
- "这个关注点很好"

#### 第二步：提出不同

清晰、直接地说出你的不同意见，不要绕弯子。

**示例：**
- "不过我对这个问题的理解有点不一样"
- "但我认为这里不会出现你说的情况"
- "关于这个方案，我有一些顾虑"

#### 第三步：出示证据（最关键的一步）

用具体的证据支撑你的观点。证据的优先级：

| 证据类型 | 说服力 | 示例 |
|---|---|---|
| **可运行的代码/测试** | ⭐⭐⭐⭐⭐ | "我写了个测试，运行结果是..." |
| **复现步骤 + 输出** | ⭐⭐⭐⭐⭐ | "按这个步骤操作，输出是..." |
| **现有代码引用** | ⭐⭐⭐⭐ | "在 file.ts:123 这里，已经有 guard 了" |
| **官方文档/规范** | ⭐⭐⭐⭐ | "根据 React 文档，这个用法是推荐的" |
| **性能数据** | ⭐⭐⭐⭐ | "压测结果显示 QPS 是..." |
| **逻辑推理** | ⭐⭐⭐ | "因为 A，所以 B，因此不会 C" |
| **个人经验** | ⭐⭐ | "我之前遇到过类似的情况..." |
| **"我觉得"** | ⭐ | "我觉得这样就挺好" |

**反驳模板（带证据）：**

```
[肯定部分]

不过关于 [具体问题]，我的理解有点不一样。

[出示证据]
  - 代码证据：在 `file.ts:123`，这里有 [相关代码]
  - 测试证据：运行 `npm test -- xxx`，结果是 [输出]
  - 复现证据：按 [步骤] 操作，实际行为是 [描述]
  - 文档证据：根据 [文档链接]，正确的做法是 [说明]

所以我认为 [你的结论]。

你觉得呢？
```

#### 第四步：保持开放

最后要表现出开放的态度，邀请对方继续讨论。

**示例：**
- "你觉得呢？有没有我漏掉的情况？"
- "如果有新的信息，我愿意重新考虑"
- "你怎么看这个问题？"

---

### 常见反驳场景与话术

#### 场景 1：审查者误解了代码逻辑

```
我理解你的担心，但实际上这里的逻辑是这样的：

在 `file.ts:123`，[解释实际逻辑]
因为 [原因]，所以不会出现你说的 [问题场景]。

我跑了一下相关测试，结果是 [测试输出]，确认没问题。

是不是我哪里没说清楚？
```

#### 场景 2：建议的方案有隐藏的代价

```
你建议的方案确实更 [简洁/优雅/清晰]，但我有一个顾虑：

[说明隐藏代价，如：性能影响、兼容性问题、增加复杂度等]

对比一下：
  - 当前方案：[优点/缺点]
  - 建议方案：[优点/缺点]

考虑到 [当前约束/优先级]，我觉得当前方案更合适。你怎么看？
```

#### 场景 3：问题存在但不值得现在修

```
你指出的问题确实存在，但我觉得可以先记下来，以后再优化，因为：

  1. [理由1：如 这部分代码后面要重构，现在改了也是白改]
  2. [理由2：如 修改风险大于收益，当前没有触发条件]
  3. [理由3：如 当前优先级是 xxx，这个改动不在范围内]

我已经记到 TODO 里了，[说明什么时候/什么条件下会处理]。

你觉得可以吗？
```

#### 场景 4：纯主观风格偏好

```
我理解你的偏好，不过关于代码风格，我的想法是：

[说明你的理由，或引用项目规范]

这个属于风格选择，不影响功能。如果项目有明确规范我就按规范来，否则我们可以保留各自的写法。你觉得呢？
```

## 注意事项与最佳实践

### ✅ 应该做的

1. **先验证再回应** —— 打开代码、运行测试，用事实说话
2. **保持好奇心** —— "为什么审查者会这么想？是不是有什么我没看到的？"
3. **对事不对人** —— 讨论的是代码，不是人。批评代码，不批评人
4. **承认错误** —— 被指出问题时，大方承认，不要找借口
5. **感谢反馈** —— 无论是否同意，有人花时间看你的代码都值得感谢
6. **具体到代码** —— 讨论时引用具体的文件、行号、代码片段
7. **愿意被说服** —— 如果对方说得有道理，大方改变想法

### ❌ 不应该做的

1. **表演式同意** —— 嘴上说"好的好的"，心里根本不认同，也不打算改
2. **为了赢而争论** —— 目标是找到正确答案，不是证明你是对的
3. **人身攻击** —— "你不懂"、"水平不行"这类话绝对不能说
4. **转移话题** —— 被指出问题时扯别的，不正面回应
5. **阴阳怪气** —— "行吧，你说的都对" 这种态度比直接反驳还糟糕
6. **忽略反馈** —— 收到意见不回应，当没看见
7. **过度防御** —— 每条意见都要反驳，本能地拒绝任何批评

---

### ⚠️ 常见陷阱

#### 1. 确认偏差（Confirmation Bias）
只看支持自己观点的证据，忽略相反的证据。

**应对：** 主动找反例，问自己"如果我是错的，会有什么表现？"

#### 2. 沉没成本谬误
"我已经写了这么多了，不能改"。

**应对：** 代码写了多少不重要，正确才重要。删掉重写是正常的。

#### 3. 权威服从
"他是 senior/架构师，他说的肯定对"。

**应对：** 职位不代表正确。用技术依据判断，不是用头衔判断。

#### 4. 从众心理
"大家都这么说，那应该是对的"。

**应对：** 多数人的意见不一定对。自己验证，独立判断。

#### 5. 输赢心态
把代码审查当成辩论，一定要赢。

**应对：** 代码审查是协作，不是对抗。目标是让代码更好，不是谁赢谁输。

## 红牌警告

以下行为是绝对禁止的，一旦出现就是严重问题：

- ❌ **表演式同意** —— 嘴上答应，实际不改，自欺欺人
- ❌ **人身攻击** —— 对审查者进行个人攻击或贬损
- ❌ **忽略 Critical 问题** —— 明知有严重问题还带着上线
- ❌ **伪造证据** —— 为了反驳而编造测试结果或数据
- ❌ **阴阳怪气** —— 用讽刺、挖苦的语气回应审查意见
- ❌ **报复性审查** —— 因为别人审查了你，你就故意找茬审回去
