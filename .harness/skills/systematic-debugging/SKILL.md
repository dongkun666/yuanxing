# Systematic Debugging — 系统化调试

## 触发条件

**必须激活：**
- 任何测试失败
- 功能 bug / 异常行为
- 性能问题
- 构建失败
- 前后端联调问题
- "明明应该工作但就是不行"的情况

**尤其要用：**
- 时间紧 / 紧急修复（越急越不能乱试）
- "就一个小问题"看起来很简单
- 已经试了 2 个 fix 还不行
- 上一个 fix 没完全解决

## 核心原则

> **铁律：没找到根因，绝对不写修复代码。修症状 = 失败。**

- 乱试比系统调试慢 10 倍
- 每个 fix 都要有假设支撑
- 试了 3 次还不行 → 停，质疑架构
- 95% 的"找不到根因"都是调查不彻底

## 四阶段流程

### 阶段 1：根因调查（最重要！）

**在想任何 fix 之前，先做这些：**

#### 1.1 仔细读错误信息
- 不要跳过任何 error / warning
- 完整读 stack trace
- 记下行号、文件路径、错误码
- 前端：看 Console + Network tab
- 后端：看 FastAPI 日志 + traceback

#### 1.2 稳定复现
- 能稳定触发吗？
- 精确步骤是什么？
- 每次都出现吗？
- 不能稳定复现 → 先收集更多数据，别猜

**LexPrime 复现清单：**
- 前端：清缓存了吗？Tailwind rebuild 了吗？
- 后端：服务启了吗？端口对吗（3847/8088/8089）？
- 数据：测试数据和生产数据有区别吗？
- 环境：是 Windows / macOS / Linux？

#### 1.3 查最近改动
- `git diff` / `git log` 看最近改了什么
- 新依赖？配置变更？
- 环境差异？

#### 1.4 多组件系统：分层加日志
**当系统有多层（前端 → 后端 → AI → OCR → DB）时：**

在每个组件边界加诊断日志：
```
对每个组件边界：
- 记录输入数据
- 记录输出数据
- 验证环境/配置是否传到位
- 检查每一层的状态

跑一次，收集证据，看哪一层坏了
然后专注调查那一层
```

**LexPrime 分层检查模板：**
```bash
# Layer 1: 前端浏览器
console.log("=== 前端发出请求 ===", payload)
# 看 Network tab: Request URL / Method / Status / Response

# Layer 2: FastAPI 后端 (端口 3847)
# 看终端日志: 请求路径 / 方法 / 状态码 / 错误栈
curl -X POST http://localhost:3847/api/endpoint -H "Content-Type: application/json" -d '{}'

# Layer 3: AI 服务 (端口 8088)
# 看 AI 服务日志: 收到的请求 / 模型输出 / 错误
curl http://localhost:8088/health

# Layer 4: OCR 服务 (端口 8089)
# 看 OCR 服务日志
curl http://localhost:8089/health

# Layer 5: 数据层 (SQLite / LanceDB)
# 直接查库验证
sqlite3 data/cases.db "SELECT * FROM ... LIMIT 5;"
```

#### 1.5 回溯数据流
**错误在调用栈深处时：**
- 错误值从哪来的？
- 谁调用了这个函数，传了错的值？
- 一直往上追，找到源头
- 在源头修，不要在症状处修

### 阶段 2：模式分析

**找到模式再修：**

1. **找工作的例子**
   - 代码库里类似的功能有没有正常工作的？
   - 哪个页面/接口是好的？

2. **对比参照**
   - 好的和坏的，有什么不一样？
   - 列出所有差异，不管多小
   - 不要假设"这个不可能有影响"

3. **理解依赖**
   - 这个功能依赖什么其他组件？
   - 什么配置 / 环境变量？
   - 有什么隐含假设？

### 阶段 3：假设与验证

**科学方法：**

1. **提出单一假设**
   - 写下来："我认为 X 是根因，因为 Y"
   - 要具体，不能模糊

2. **最小化测试**
   - 做最小的改动来验证假设
   - 一次只改一个变量
   - 不要同时改多个东西

3. **验证后再继续**
   - 有用 → 阶段 4
   - 没用 → 提新假设，重来
   - 不要在上面叠加更多 fix

4. **搞不懂就说出来**
   - "我不理解 X"
   - 别装懂
   - 找人求助 / 查文档

### 阶段 4：实施修复

**修根因，不修症状：**

1. **先写失败的测试**
   - 最简单的复现代码
   - 有测试框架就写自动化测试
   - 没有就写个一次性脚本
   - **修之前必须有**

2. **实施单一修复**
   - 只针对找到的根因
   - 一次一个改动
   - 不要"顺便"改进 / 重构
   - 不要捆绑其他改动

3. **验证修复**
   - 测试通过了吗？
   - 其他测试没坏吧？
   - 问题真的解决了吗？

4. **修了还不行？**
   - 停！
   - 数一下：试了几个 fix 了？
   - < 3 个 → 回到阶段 1，用新信息重新分析
   - **≥ 3 个 → 停，质疑架构（见下方）**

5. **3 次以上失败：质疑架构**

**信号：**
- 每个 fix 都在不同地方暴露新问题
- fix 需要"大重构"才能做
- 每个 fix 都会在别的地方制造新症状

**停下来问根本问题：**
- 这个模式本身对吗？
- 我们是不是"纯靠惯性在坚持"？
- 应该重构架构，还是继续修症状？

**和用户讨论后再继续。**

## 危险信号 — 停，回到流程

如果你在想这些，立刻停：
- "先快速修一下，以后再调查"
- "试试改 X 看行不行"
- "多改几个地方一起跑"
- "跳过测试，我手动验证就行"
- "应该是 X，我直接修了"
- "不完全懂但也许有用"
- "模式说 X 但我改改也行"
- "主要问题是这些：[没调查就列一堆 fix]"
- 还没追踪数据流就提方案
- **"再试一次"（已经试了 2 次以上）**
- **每个 fix 都在不同地方出新问题**

**全部都是：停。回到阶段 1。**

## 常见借口

| 借口 | 现实 |
|------|------|
| "问题简单，不用走流程" | 简单问题也有根因。流程对简单 bug 更快。 |
| "紧急，没时间走流程" | 系统调试比瞎试快得多。 |
| "先试试这个，不行再调查" | 第一个 fix 会定调子。从一开始就做对。 |
| "等确认能修好再写测试" | 没测试的 fix 站不住。先写测试才能证明。 |
| "一次改多个省时间" | 不知道哪个起作用的。还会造新 bug。 |
| "参考太长，我改改就行" | 一知半解必出 bug。完整读。 |
| "我知道问题在哪，直接修" | 看到症状 ≠ 理解根因。 |
| "再试一次就好"（2 次失败后） | 3 次失败 = 架构问题。别再试了。 |

## 快速参考

| 阶段 | 核心动作 | 成功标准 |
|------|----------|----------|
| **1. 根因** | 读错误、复现、查改动、收集证据 | 知道 WHAT 和 WHY |
| **2. 模式** | 找工作的例子、对比 | 找出差异 |
| **3. 假设** | 提理论、最小验证 | 确认或否定假设 |
| **4. 实施** | 写测试、修、验证 | bug 解决，测试通过 |

## LexPrime 特有调试清单

### 前端问题
- [ ] Tailwind rebuild 了吗？
- [ ] 清浏览器缓存了吗？
- [ ] view 的 `hidden view-content` class 对吗？
- [ ] `switchView()` 调用了吗？
- [ ] IIFE 初始化顺序对吗？
- [ ] globalThis 桥接有没有问题？
- [ ] Console 有没有 JS error？

### 后端问题
- [ ] 服务启了吗？端口对吗？
- [ ] 请求路径对吗？方法对吗？
- [ ] Pydantic 模型校验过了吗？
- [ ] 数据库连接正常吗？
- [ ] 看完整 traceback 了吗？

### 跨服务问题
- [ ] 前端发的请求和后端期望的一致吗？
- [ ] 请求头（Content-Type 等）对吗？
- [ ] 响应格式是前端期望的吗？
- [ ] 错误码和错误信息处理了吗？

## 常见陷阱

- ❌ "就改一行看看" → 一行也可能是错的方向
- ❌ 同时改 3 个地方 → 不知道哪个起作用
- ❌ 在症状处加判断绕过 → 根因还在，迟早再爆
- ❌ 跳过测试 "我手动测过了" → 下次回归还得手动测
- ❌ 试了 3 次还在试 → 该质疑架构了
