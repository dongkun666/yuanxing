# Systematic Debugging — 系统化调试

**核心理念：系统化而非临时方案，用证据而非猜测。** 通过严格的 4 阶段流程，确保不遗漏任何可能性，找到真正的根本原因，而不是停留在表面症状。

> "调试不是猜谜，是科学方法。" —— 佚名

---

## 何时激活

### 必须激活（强场景）

- 任何 bug 修复任务（无论大小）
- 功能异常、行为不符合预期
- 性能问题（慢、卡顿、内存泄漏）
- 前后端联调问题（接口对不上、数据不一致）
- 偶发问题/间歇性故障
- 用户明确说"调试一下"、"找原因"、"为什么会这样"
- 任何你需要搞清楚"为什么"的场景

### 建议激活（中场景）

- 修改代码后测试失败
- 新功能集成时出现问题
- 第三方库/API 行为不符合预期
- 环境问题（本地正常、线上异常）
- 你怀疑有 bug 但不确定具体位置

### 跳过（弱场景）

- 纯新功能开发（没有现有问题需要调试）
- 明确的需求变更（不是 bug，是需求变了）
- 简单的 typo 修复（一眼就能看出来的问题）
- 用户明确说"不用找原因，直接改"（但要警惕掩盖深层问题）

## 4 阶段根本原因流程

系统化调试的核心是四个阶段，**必须按顺序执行，绝对不要跳步**。

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  1. 复现问题  │────▶│  2. 定位根因  │────▶│  3. 制定修复  │────▶│  4. 验证修复  │
│  Reproduce  │     │   Diagnose   │     │     Fix     │     │   Verify    │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
       ▲                                                         │
       └─────────────────────────────────────────────────────────┘
                           （验证失败 → 回到第 1 步）
```

> ⚠️ **黄金法则：** 如果你不能复现问题，你就不可能真正修复它。

---

### 第一阶段：复现问题（Reproduce）

**目标：** 找到可靠的、可重复的问题触发方式。没有稳定复现，后续一切都是空谈。

#### 步骤

1. **收集信息** — 问题描述、错误日志、截图、操作步骤
2. **还原环境** — 确保你的环境和问题发生时一致（版本、配置、数据）
3. **尝试复现** — 按照描述的步骤操作，看能否触发问题
4. **简化复现路径** — 去掉无关步骤，找到最短的触发路径
5. **确认复现率** — 是 100% 必现，还是偶发？偶发的话频率如何？

#### 复现问题的检查清单

- [ ] 你能在本地/测试环境复现这个问题吗？
- [ ] 复现步骤是清晰的、可重复的吗？
- [ ] 你知道哪些条件是必须的（哪些是无关的）？
- [ ] 如果是偶发问题，你能提高复现概率吗？

#### 复现不了怎么办？

| 情况 | 应对策略 |
|------|----------|
| **环境差异** | 检查代码版本、依赖版本、配置文件、环境变量、数据 |
| **数据相关** | 确认是否和特定数据/用户/状态有关 |
| **时序问题** | 加日志、加断点、放慢速度观察 |
| **并发问题** | 增加并发数、加锁、用压力测试工具 |
| **完全没思路** | 回到第 1 步，收集更多信息，不要猜 |

> 💡 **经验法则：** 花在复现上的时间永远值得。复现越稳定，定位越快。

---

### 第二阶段：定位根因（Diagnose）

**目标：** 找到问题的真正根本原因，而不是表面现象。

#### 定位方法论：假设驱动 + 实验验证

```
提出假设 → 设计实验 → 执行实验 → 验证假设 → 是/否 → 下一个假设
```

**关键原则：**
- 一次只验证一个假设
- 每个假设都要有可观测的验证方法
- 用证据说话，不要靠感觉

#### 常用定位技术

##### 1. 二分法（Bisect）

把范围一分为二，逐步缩小问题所在区域。

- **代码二分：** `git bisect` — 找到引入 bug 的那次提交
- **逻辑二分：** 注释掉一半代码，看问题是否还在
- **时间二分：** 在流程中间加断点/日志，看问题出在前面还是后面

##### 2. 自顶向下 vs 自底向上

| 方法 | 做法 | 适用场景 |
|------|------|----------|
| **自顶向下** | 从入口开始，一步步往下追 | 对系统不熟悉、不知道问题在哪 |
| **自底向上** | 从错误点开始，往回找根源 | 有明确的错误位置或栈追踪 |
| **中间突破** | 从你最熟悉的地方开始 | 对系统部分熟悉，猜测问题可能在附近 |

##### 3. 差异对比法

对比"正常"和"异常"的差异：

- 正常的请求 vs 出问题的请求
- 正常的数据 vs 出问题的数据
- 正常的环境 vs 出问题的环境
- 昨天能跑的代码 vs 今天挂了的代码

问自己：**有什么不一样？**

##### 4. 日志分析法

- 仔细阅读错误信息和栈追踪（不要只看最后一行！）
- 在关键位置加日志，观察变量值和执行路径
- 打开调试模式/详细日志级别
- 对比正常流程和异常流程的日志差异

#### 定位根因的检查清单

- [ ] 你能指出问题出在具体哪一行/哪一个函数吗？
- [ ] 你知道为什么这行代码会导致问题吗？
- [ ] 你排除了其他可能性吗？
- [ ] 你能用实验证明你的假设是对的吗？

> ⚠️ **常见陷阱：** 不要找到一个"可能的原因"就停下来。确认它，排除其他可能。

---

### 第三阶段：制定修复（Fix）

**目标：** 针对根本原因制定修复方案，确保修复的是"因"而不是"果"。

#### 修复的层次

| 层次 | 说明 | 例子 |
|------|------|------|
| **L1：临时补丁** | 掩盖症状，问题还在 | 捕获异常然后忽略 |
| **L2：表面修复** | 修了这个场景，但类似场景还会出问题 | 只处理了这个特定输入 |
| **L3：根本修复** | 解决了根本原因，同类问题不会再出现 | 修复了算法逻辑缺陷 |
| **L4：深度防御** | 不仅修了，还加了防护，即使再出问题也容易发现 | 修复 + 断言 + 日志 + 监控 |

**目标是至少达到 L3，最好能到 L4。**

#### 制定修复方案的步骤

1. **理解根本原因** — 确保你真的搞懂了为什么会出问题
2. **设计修复方案** — 怎么改才能解决根本原因？
3. **评估影响范围** — 改了这里，会影响哪些地方？
4. **考虑风险** — 修复会不会引入新问题？
5. **选择方案** — 如果有多个方案，选最稳妥的那个

#### 修复的原则

- **最小改动原则** — 只改必须改的，不要"顺便"重构
- **向后兼容** — 不要破坏现有功能和接口
- **可回滚** — 如果修复有问题，能快速回退
- **有测试保护** — 至少加一个回归测试

---

### 第四阶段：验证修复（Verify）

**目标：** 证明修复有效，且没有引入新问题。

#### 验证的层次

1. **验证问题解决了** — 原来的复现步骤现在不会出问题了
2. **验证没有破坏现有功能** — 相关的测试都能通过
3. **验证边界情况** — 类似的场景、边界条件都没问题
4. **（可选）验证性能** — 修复没有带来性能退化

#### 验证清单

- [ ] 原来的复现步骤现在正常了吗？
- [ ] 相关的单元测试/集成测试都通过了吗？
- [ ] 你测试了边界情况吗？（空值、极端值、异常输入）
- [ ] 你检查了相关的代码路径吗？
- [ ] 如果是并发/时序问题，你做了压力测试吗？

> 💡 **重要：** 验证失败时，**不要直接在修复上打补丁**。回到第 1 步，重新分析，可能你找的根因不对。

## 根本原因追踪技术

### 5 Whys 分析法

连续问 5 个"为什么"，挖到最根本的原因。

**例子：**
```
问题：服务器返回 500 错误
  Why？ → 数据库查询超时了
  Why？ → 查询没有走索引，全表扫描太慢
  Why？ → 新增的查询条件没有建索引
  Why？ → 开发时没考虑到数据量增长的情况
  Why？ → 没有性能评审流程
根本原因：缺少性能评审机制
```

### 鱼骨图（石川图）

从多个维度分析可能的原因：

```
                    问题
                     │
     ┌───────────────┼───────────────┐
     │               │               │
   人员             流程            技术
     │               │               │
  - 经验不足      - 需求不清      - 代码bug
  - 沟通不畅      - 测试不足      - 设计缺陷
  - 操作失误      - 评审缺失      - 依赖问题
```

### 因果链追踪

从现象出发，沿着因果链一直追溯：

```
现象 → 直接原因 → 间接原因 → 根本原因
```

每一步都要问：**"为什么会这样？"** 和 **"这是唯一的原因吗？"**

## 深度防御策略

修复 bug 时，不要只满足于"修好了"，要考虑多层防御：

### 第一层：错误检测

- **断言（Assertion）** — 在关键位置加断言，不满足条件时立刻失败
- **输入校验** — 对外部输入做严格校验，尽早发现问题
- **健康检查** — 定期检查系统状态，异常时报警

### 第二层：错误隔离

- **熔断/降级** — 依赖出问题时，不要拖垮整个系统
- **超时控制** — 所有外部调用都要有超时
- **资源限制** — 防止单个请求占用过多资源

### 第三层：可观测性

- **详细日志** — 关键路径、关键变量、异常情况都要记录
- **指标监控** — 错误率、延迟、吞吐量等指标
- **链路追踪** — 分布式系统中追踪请求的完整路径

### 第四层：快速恢复

- **优雅降级** — 部分功能不可用时，核心功能还能用
- **自动重试** — 临时性故障自动重试
- **回滚机制** — 出问题时能快速回滚到上一个版本

> 💡 **理念：** 假设系统一定会出问题，在此基础上设计防御。

## 条件等待技巧

调试异步、并发、时序相关问题时的实用技巧：

### 1. 加日志，不要用断点

断点会改变线程调度，可能让并发问题消失（"观察者效应"）。日志更可靠。

### 2. 时间戳 + 线程ID

日志里加上精确的时间戳和线程/协程 ID，方便分析时序。

### 3. 延迟注入

故意在某些位置加延迟，看是否能稳定复现时序问题。

### 4. 压力测试

用工具加大并发量、提高请求频率，让偶发问题更容易出现。

### 5. 状态快照

在关键节点打印完整的状态，而不是只打印你觉得"相关"的变量。

## 常见调试陷阱

### ❌ 陷阱 1：猜谜式调试

**表现：** 不收集信息，不分析，上来就改代码试，"这样改试试？那样改试试？"

**问题：**
- 效率极低，纯靠运气
- 很容易引入新 bug
- 即使碰巧"修好了"，也不知道为什么好的

**纠正：** 停下来，先收集信息，再提出假设，然后验证。

---

### ❌ 陷阱 2：只看表面，不挖根因

**表现：** 看到报错就加个 try-catch，看到空指针就加个 if 判断，完事。

**问题：**
- 问题只是被掩盖了，根源还在
- 以后会在其他地方以其他形式爆发
- 代码里到处都是"补丁"，越来越难维护

**纠正：** 多问几个"为什么"，找到真正的原因。

---

### ❌ 陷阱 3：确认偏差

**表现：** 脑子里先有了一个"肯定是这个原因"的想法，然后只找支持这个想法的证据，忽略矛盾的证据。

**问题：**
- 容易误入歧途，在错误的方向上越走越远
- 明明证据已经指向其他原因了，就是看不见

**纠正：** 主动寻找"证伪"的证据。问自己："什么情况下我的假设是错的？"

---

### ❌ 陷阱 4：改太多

**表现：** 调试的时候"顺便"改了一堆东西，重构、优化、清理代码...

**问题：**
- 最后不知道是哪个改动把问题修好了
- 很可能引入了新问题
- 回滚困难

**纠正：** 调试阶段只做最小改动。重构等 bug 修好了、验证过了再说。

---

### ❌ 陷阱 5：忽略环境因素

**表现：** "我本地好的啊"、"昨天还能跑的"，然后就卡住了。

**问题：**
- 代码版本、依赖版本、配置、数据、环境变量、操作系统... 任何一个不一样都可能导致问题
- "本地好的"不代表"代码没问题"

**纠正：** 系统地对比环境差异，一个一个排除。

---

### ❌ 陷阱 6：过早下结论

**表现：** 看到一点线索就立刻断定"就是这个问题"，然后开始修。

**问题：**
- 可能找错了原因，白忙活一场
- 真正的原因被忽略了

**纠正：** 找到一个可能的原因后，先验证它，再排除其他可能。确认了再动手修。

## LexPrime 项目适配

LexPrime 是前后端分离项目（Python 后端 + JavaScript 前端），调试时需要特别注意跨层问题。

### 前后端联调问题调试法

当你遇到"前端显示不对"、"接口数据不对"这类问题时，按以下步骤定位：

#### 第一步：确定问题在哪一层

**核心问题：是前端的锅，还是后端的锅？**

用浏览器开发者工具（F12）检查：

1. **看 Network 面板** — 请求发出去了吗？URL 对吗？参数对吗？
2. **看 Response** — 后端返回了什么？状态码是多少？响应体对吗？
3. **对比预期** — 返回的数据和前端期望的一致吗？

| 现象 | 问题在哪 |
|------|----------|
| 请求没发出去 | 前端问题 |
| 请求 404/405 | 前端 URL 错了，或后端路由不对 |
| 请求 400 | 前端参数格式/内容不对 |
| 请求 500 | 后端报错 |
| 请求 200 但数据不对 | 后端逻辑问题 |
| 请求 200 数据对但显示不对 | 前端渲染问题 |

#### 第二步：后端调试

如果确定是后端问题：

1. **看后端日志** — 有没有报错？栈追踪是什么？
2. **复现请求** — 用 curl / Postman 直接调后端接口，绕过前端
3. **定位代码位置** — 根据接口 URL 找到对应的 handler / controller
4. **加日志/断点** — 观察入参、中间变量、返回值
5. **追踪调用链** — 从 controller → service → repository → database

**Python 后端调试技巧：**
- 用 `print()` 或 `logging` 模块打日志
- 用 `pdb` 或 IDE 断点调试
- 用 `pytest` 写测试单独验证某个函数
- 检查数据库中的实际数据，不要假设数据是对的

#### 第三步：前端调试

如果确定是前端问题：

1. **打开浏览器 DevTools** — F12
2. **看 Console 面板** — 有没有 JS 报错？
3. **看 Network 面板** — 请求和响应是什么样的？
4. **用 debugger 打断点** — 在关键位置加 `debugger` 语句，单步执行
5. **检查组件状态** — 用 React/Vue DevTools 看 state/props

**前端调试技巧：**
- `console.log()` 打日志，但注意不要留到生产环境
- 条件断点 — 只在特定条件下断住
- 网络节流 — 模拟慢网络，看 loading 状态是否正确
- 清除缓存 — 有时候是缓存导致的老问题

#### 第四步：数据一致性校验

前后端联调最常见的问题之一是**数据格式不一致**：

- 字段名不一致（`user_name` vs `userName`）
- 数据类型不一致（数字 vs 字符串）
- 日期格式不一致（时间戳 vs ISO 字符串）
- 嵌套结构不一致
- 空值处理不一致（`null` vs `undefined` vs `""`）

**调试方法：**
1. 打印完整的请求/响应数据
2. 和接口文档对比（如果有文档的话）
3. 前后端坐下来（或坐下来自己跟自己）对一遍字段定义
4. 写类型定义（TypeScript / Pydantic），让编译器帮你抓错

### Python 后端调试工具

#### 日志调试

```python
import logging

logger = logging.getLogger(__name__)

def some_function(x, y):
    logger.debug(f"进入 some_function, x={x}, y={y}")
    result = x + y
    logger.debug(f"some_function 返回: {result}")
    return result
```

#### pdb 调试

```python
import pdb

def problematic_function():
    x = calculate_something()
    pdb.set_trace()  # 程序会在这里停下，进入交互调试
    y = process(x)
    return y
```

常用 pdb 命令：
- `n` / `next` — 执行下一行
- `s` / `step` — 进入函数
- `c` / `continue` — 继续执行
- `p 变量名` — 打印变量值
- `l` / `list` — 显示当前位置的代码
- `q` / `quit` — 退出

#### pytest 调试

写一个测试用例来复现问题：

```python
def test_something_fails():
    # 复现问题的步骤
    result = problematic_function()
    assert result == expected  # 断言失败，帮你定位问题
```

### JavaScript 前端调试工具

## 注意事项

### ✅ 应该做的

1. **按流程来** — 复现 → 定位 → 修复 → 验证，不要跳步
2. **用证据说话** — 每一个结论都要有证据支撑
3. **记录过程** — 你试过什么、发现了什么、排除了什么
4. **保持怀疑** — 对自己的假设也要保持怀疑
5. **小步验证** — 每次只改一点，改完就验证
6. **写回归测试** — 修完 bug 加个测试，防止以后再犯
7. **及时求助** — 卡太久了就找人讨论，不要硬扛
8. **复盘总结** — 修完 bug 想想：为什么会出现？以后怎么避免？

### ❌ 不应该做的

1. **不要猜** — 猜谜式调试效率最低
2. **不要跳步** — 还没复现就开始修，大概率白忙活
3. **不要改太多** — 调试时不要顺便重构
4. **不要停在表面** — 多问几个为什么，挖到根因
5. **不要忽略矛盾的证据** — 跟你的假设不符的证据更重要
6. **不要害怕回滚** — 修复不对就回滚，重新分析
7. **不要留调试代码** — `console.log`、`print`、`debugger` 要清理
8. **不要忘了更新文档** — 如果行为变了，文档也要更

## 与其他技能的关系

| 技能 | 关系 | 说明 |
|------|------|------|
| **test-driven-development** | 互补 | TDD 预防 bug，调试解决已出现的 bug。修 bug 时先写测试复现，再修复 |
| **writing-plans** | 上游 | 复杂的调试任务可以先做计划，再按计划执行 |
| **executing-plans** | 并行 | 按计划执行调试步骤，每步验证 |
| **requesting-code-review** | 下游 | 修复完成后，可以请人 review 修复方案 |
| **git-commit** | 并行 | 修复完成后提交，commit message 说明问题和原因 |
| **brainstorming** | 辅助 | 定位根因遇到瓶颈时，可以 brainstorm 可能的原因 |

```
发现 bug → systematic-debugging → 修复完成 → 回归测试 → 提交
                ↑                     ↑
                │                     │
         test-driven-development  code-review
```

## 红牌警告

出现以下情况，说明你的调试方法可能有问题：

- ❌ 你已经改了好几版了，但问题还没解决
- ❌ 你说"应该好了吧"，但不确定到底好没好
- ❌ 你改了很多地方，但不知道具体是哪一改动生效的
- ❌ 问题有时候出现有时候不出现，你说"可能是环境问题"
- ❌ 你已经调试了半小时，还不知道问题大概在哪
- ❌ 你不停的改代码试，没有任何明确的假设
- ❌ 你发现了一个"原因"，但解释不了所有现象
- ❌ 修复了之后，你觉得"应该不会再出了"，但没什么把握

> ⚠️ **停下来！** 如果你遇到以上情况，说明你需要：
> 1. 回到第 1 步，重新整理信息
> 2. 把你的假设和证据写下来
> 3. 找个人讨论一下
> 4. 可能你需要换个思路
